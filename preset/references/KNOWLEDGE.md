# Knowledge Engineering Policy

这套知识层治理原则供 `init` / `plan-feature` / `build-feature` / `review-feature` / `doc-audit` 共同遵守。核心问题：让 AI 在业务仓库里写对代码，需要什么样的知识、放在哪、谁维护。

## 为什么（WHY）

AI 是「词汇的自信放大器」，而且它抽掉了人类之间的**澄清摩擦**。人接到一个含糊术语会追问「你说的 X 是指哪个 X」；AI 不会问——它会自信地按自己那套理解去实现，然后编译通过、测试通过、生产炸掉。含糊、同名异义、错配的业务词，不会以报错的形式暴露，而是以「看起来对但语义错」的代码落地。

结论：业务知识不能只活在人脑或散落的会议记录里，必须**白纸黑字、code-adjacent**（贴着代码、随代码版本化），让 AI 在动手前能显式加载到正确的、唯一的那份事实。

## 知识 vs 流程分离

两类东西，两个位置，别混：

- **知识**——AI 要「知道」的事实：`docs/`（业务语言、规则、架构）与 `.claude/rules/*`（路径绑定的硬约束）。
- **流程**——AI 要「按步骤做」的事：`.claude/skills/*`（开发 SOP）。

**skill 只引用知识，不复制知识。** 一旦 skill 里抄了一份规则副本，它就会和真源漂移。skill 应当说「动手前先读 `docs/domain/BUSINESS-RULES.md`」，而不是把规则正文粘进来。

## 单一真源

每条事实只有**一个** owner 层。不要在多个文件里重复同一条业务规则或定义——重复必然漂移，改了一处忘了另一处。要改，就改那唯一的一处。`doc-audit` 的 Step 4 路由表就是这条原则的执行细则。

## Bounded Context

一个上下文一套语言。**同一个词在不同上下文里是不同实体**（「订单」在销售域和履约域可能指不同的东西）。

**禁止把不同实体拉平成一个带 `type` 字段的泛类。** 那会抹掉精度——AI 会以为它们是一种东西，跨上下文套用错误的字段和规则。`GLOSSARY` 按 bounded context 分块，每块维护自己那套词汇。

## 命名即词汇决策

表名、字段名、函数名、API 名、工具名——每一次命名都在**改变 AI 的行为**，因为 AI 高度依赖名字去推断语义。坏命名（误导性的、和业务说法冲突的、同名异义的）有两条出路：要么改掉命名，要么在 `GLOSSARY` 里标注「避免叫法 / 实际含义」，把陷阱显式化。别放任一个误导性的名字在代码里，指望注释去救。

## 薄根 + 渐进披露

- `AGENTS.md` 保持 < 150 行，**只放指针**，不放正文。它是目录，不是百科。
- 靠「动手前先读 X」这样的**显式指针**去按需加载 `docs/`，**别指望 skill 自动触发**——实测 skill 的自触发率低，把关键知识押在自动触发上会漏读。
- **别把 linter / 类型系统能强制的东西写进文档**（缩进、类型、格式）。那些交给工具当真源，文档只写工具管不了的业务语义。写进文档反而多一处会漂移的副本。

## docs/domain vs 外部知识库的边界

- **AI 写码要加载的业务知识 → 进仓库 `docs/`**：随代码版本化、进 PR review、和代码一起演进。
- **跨项目的历史 / 决策 / handoff / 个人工作记忆 → 留在用户的外部知识库**（如 Obsidian）。
- 同一条事实**不双写**。业务定义属于仓库 docs/，就别在外部知识库再抄一份；反之亦然。双写 = 保证漂移。

## 红线

- `GLOSSARY` / `BUSINESS-RULES` 等业务知识，**永远在人 + 业务 review 之后才当定稿**。AI 可以起草，但不能拍板业务事实。
- **别让 AI 全自动生成整套文档。** 实测全自动生成整套文档反而**降低任务成功率、增加 token 消耗**——生成的是听起来对、实则未经业务校验的内容，污染真源。文档要小步、可 review 地增补。
- 给每条知识**标可信度**：`validated`（人验过）/ `inferred-from-code`（从代码推断，未经业务确认）/ `unverified`（待核）。让下游 AI 知道哪些能信、哪些要小心。
