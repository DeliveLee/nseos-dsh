# Quality and Evaluation Policy

> **本文件管「要检查什么、什么算证据」。「这项检查到底能不能区分好与坏」由 `VERIFICATION.md` 独家负责**(判别力四问、L0–L4、变异验证、三类已知假绿、恒真断言)——那里是唯一真源,本文件不复制它的判据表。两者的分工:本文件说「拿活路径证据,别拿绿测试顶」,那边说「你拿到的这条活路径证据,在产品坏掉时会不会照样是绿的」。

## Evidence hierarchy

1. 在真实运行的应用上驱动受影响流程得到的活路径证据（真实 UI 走查、控制台、网络、日志、截图、真实接口返回）。
2. 可重复的自动化测试、构建、静态检查和运行观测。
3. 人工验收或截图/日志等可审计证据。
4. 仓库差异和明确的代码推理。
5. 独立 Agent 评审。
6. 实现 Agent 的自我评价。

低层证据不能替代高层证据。例如评审 Agent 说“测试很好”不能替代实际测试结果。**面向用户的改动，绿测试不能替代活体 UI/活路径走查**：代码级审计 + 绿单测会系统性漏掉运行期 UX 和功能缺陷（字段显示原始 ID、上传被全局配置破坏、筛选触发整页闪烁等），二者必须并行；缺活路径走查即视为该项验证未完成。

缺活路径证据时，功能状态是 `PENDING_LIVE_VERIFY`，不得标记为 done、verified、`READY_FOR_INTEGRATION` 或 released 类状态。当需求或所报缺陷针对的正是真实路径时，在 mock/stub 栈上的验证不满足活路径验证。推迟活路径验证（推到迁移期、推到后续会话或推给用户）是显式例外，必须作为具名 PENDING 项记入 `FEATURE_STATE.md` 与 Handoff；在叙述里披露不解除该门禁——诚实披露不等于通过门禁。

## Required checks by risk

| Risk | Minimum checks |
|---|---|
| Low | 相关单元测试、lint/类型检查、差异审查 |
| Medium | Low + 集成测试、关键错误路径、权限与回归检查 |
| High | Medium + 安全审查、迁移/回滚演练、端到端验证、人工批准 |

任何风险等级下，只要改动用户可见，就必须附活路径走查证据。

## Adversarial verification

- 「全面 / 彻底 / 审计 / 上线前」级别的检查，以及 Complex/Exceptional 变更类：按维度扇出多个独立 reviewer，每条发现交给独立怀疑者对抗验证——默认证伪，证不掉才保留。单 reviewer 一次通过仅适用于 Small/Standard 变更。
- 符合性验证（对象是否符合设计稿/需求/规范真值）必须与改动验证（本次 diff 是否生效）分开执行：验证清单从目标真值推导，不从本次 diff 推导；由不知道改了什么的盲验 verifier 只拿真值 + 活对象输出全部失配清单，主会话只裁决。
- 小尺寸元素（图标/徽标/缩略图）必须 1:1 或放大逐个比对；整页缩略截图对它们检出率≈0，不算验证。
- N 个对象 = N 份完整检查矩阵，禁止「第 1 个验过 → 其余推断通过」。

## Product completeness dimensions

对用户可见功能至少检查：发现入口、主流程、详情、搜索/筛选/排序/分页的适用性、权限、验证、空状态、加载、错误、重试、可访问性、响应式、审计、通知、撤销/确认以及帮助文本。不是所有维度都必须实现，但每项必须被判断为 Required、Expected、Optional 或 Not applicable。

## System evaluation

试点前建立基线，按功能持续记录：

- 从批准到可集成的 lead time；
- 部署频率；
- change fail rate；
- deployment rework rate；
- failed deployment recovery time；
- 逃逸缺陷；
- PR/评审返工轮数；
- 人类主动工作时间和等待时间；
- 模型调用成本和端到端耗时；
- AI 生成代码被接受、重写或删除的比例；
- Feature Contract 验收标准的证据覆盖率。

## Release criterion for the operating model

只有当试点在不恶化稳定性和安全性的前提下，显示交付效率或人工负担有可重复改善，才扩大使用范围。单个成功案例不能证明系统有效。

## Anti-gaming

- 指标用于发现瓶颈，不作为单一绩效目标。
- 不以提交数、代码行、Agent 数或 token 数衡量产出。
- 不能通过拆小无意义任务、降低测试强度或延后缺陷来改善指标。
