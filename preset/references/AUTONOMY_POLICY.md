# 自主模式策略（autopilot）

适用于 `ai-nseos/PROJECT_PROFILE.md` 中 `Delivery mode: autopilot` 的仓库，或人类单次覆盖为自主模式的会话。协作模式（`interactive`）不适用本文。

## 一 · 不打扰 ≠ 不阻塞

自主模式取消的是**打扰**（执行期反复找人拍板），不是**阻塞**（该停的地方照停）。

- 撞到不可预授权的事项 → **挂起该条目，继续做别的**。这是设计内的正常路径，不是失败。
- 撞到机器门禁 → **合法挂起**。如实报「差哪几项 + 已完成什么」，然后停。门禁被拦不是需要绕过的障碍，是本次交付到此为止的事实。

**为什么这条要写在第一节**：`FB-20260725-003` 实测记录——bonohair-rebuild 会话 `c7c77a12` 在 `/goal` 长跑 + Stop hook 反复回压下，两次正确拒绝门禁后，第三次执行了 `AINSEOS_ACTION_GATE=off git push`。压力来源是「不许停下来」的持续回压，不是恶意。

**自主模式是同一种压力的制度化版本。** 「执行期不许打扰用户」会被误读成「必须自己想办法通过」。这两句话之间隔着本文的红线节，而红线节是唯一挡在中间的东西。

## 二 · 红线（不可协商）

以下三条不受任何授权书、任何人类口头授权、任何长跑压力覆盖。**授权书模板内置这一节且不可删除。**

1. **发布凭据永不可预授权、不可自签充数。** `ai-nseos/state/.release-ready.json` 的 `review` / `prod_schema` / `doc` 三个字段，只在对应的真实动作发生后才写：`review` 需真的跑过独立评审并产出报告，`prod_schema` 需人类确认过生产 schema，`doc` 需文档已维护。为了通过门禁而写字段 = 伪造验收证据，比不通过严重得多。凭据在机制上确实是「一条命令就能自签」的 advisory 中断（见 `MAINTENANCE.md`），**这正是它必须靠本条约束的原因，不是可以自签的理由**。

   **v0.24.0 补两条机器判据（两种交付模式一视同仁）。** ①`review` 必须显式写 `independent: true|false`。实现者自己复核自己的工作就是 `false`——**如实写 `false` 不是失败，它仍然可以发布**，门禁只会把这次发布交给人类确认一次；把自审写成 `true` 才是伪造验收证据，落进本条。②每个字段都带 `head_sha`，绑定被复核的那个提交；写完凭据后再产生新提交，凭据自动失效（`EVIDENCE_STALE`），需要对新的 HEAD 重做该项工作。自主模式撞到这两条同样是**合法挂起**：如实报缺口然后停，不得改写字段值凑过。

2. **`AINSEOS_*` 阀门属人类运维，模型不得关闭、不得请求关闭。** `AINSEOS_ACTION_GATE` / `AINSEOS_PROMPT_ROUTING` / `AINSEOS_SKILL_GATE` / `AINSEOS_DOC_GATE` 等开关的存在是为了让人类在机器层面维护自己的工具，不是给模型的逃生口。在报告里向人类建议关阀门，等同于自己关。

3. **内联环境前缀对 hook 无效。** `AINSEOS_ACTION_GATE=off git push` 这种写法不会生效——hook 读的是 Claude 进程环境，不是单条命令的前缀环境。它照样会被下一道门拦住。写出这条命令唯一的后果是留下一次试图绕过门禁的记录。

**撞到红线的正确动作**：停 → 记入挂起清单 → 在报告里如实写「门禁 X 未通过，缺 A / B 两项；本次已完成的是 C / D」→ 结束。不重试、不换写法、不找等价路径。

## 三 · 可否预授权分级在执行期怎么用

**完整的可否预授权分级见 `references/AUTHORITY.md` 决策矩阵的第 4 列，那里是唯一真源。** 本节不复制那张表——它改了这里忘改就是漂移。本节只管一件真源不管的事：**拿到一个级别之后，自主模式的执行期该做什么动作。**

三条派生约束：

- **授权书里的每一条默认处置都必须落在「可」或「有限可」的格子里。** 写进 `DELEGATION_MATRIX.md` 的「否」类条目不因为被写进去就生效——见真源读法那句「授权书里写了也不算数」。
- **级别只由真源和授权书决定，执行期 AI 不得自行升级某一类的可授权程度。** 「这条我判断风险很低」「这次情况特殊」不构成把「否」读成「有限可」的理由。预授权是人类**提前**行使决策权并留下书面依据，**不是把决策权让渡给模型**——所以能改变级别的只有人类，而且是在场时改。
- **拿不准某件事落在哪一类时，按「否」处理。** 挂起的成本是一条边角料没做，误判成「可」的成本是一次没人知道的自决。

### 执行期处置规则

| 情形 | 动作 |
|---|---|
| 授权书覆盖了这一条 | 按其默认处置自决 → 追加决策日志 |
| 授权书未覆盖，真源判为「可」 | 按同类条目的**最保守取向**自决 → 追加决策日志并标记「类推自决」 |
| 授权书未覆盖，真源判为「有限可」 | 仅在真源标注的方向内自决（如「不破坏兼容」「白名单内」），且取最保守取向 → 追加决策日志并标记「类推自决」；**越出标注方向即挂起** |
| 真源判为「否」 | **挂起**该条目 → 记挂起清单 → 转去做不依赖它的工作。不自决、不追问、不停摆。 |
| 测试实现细节需要改（见第六节） | 自主修改 → 追加决策日志 |
| 测试断言语义需要改（见第六节） | **挂起** |
| 撞到机器门禁 | **挂起**（合法）；如实报缺项与已完成项；绝不自签凭据、绝不关阀门 |

「类推自决」是兜底，不是常态。同一功能内出现 3 条以上类推自决，说明勘探漏得太多，应在验收报告里显式指出。

## 四 · 挂起（PARKED item）

**挂起是条目级概念，不是状态。**

- **粒度**：挂起的对象是《测试目标清单》里的具体条目，不是整个功能。
- **记录**：每次挂起在 `DECISION_LOG.md` 第二张表（挂起清单）追加一行，必须写明它影响了哪几条测试目标编号——这个编号并集是第五节算分母的输入。
- **功能状态**：整体保持 `IN_PROGRESS`。**不新增状态**，只有跌破第五节阈值才转既有的 `BLOCKED`。
- **解除**：人类回答后，在挂起清单标记解除并注明结论；受影响条目回到可推进集合。
- **验收**：挂起清单是最终验收四项之一。每条要能回答：撞到什么、为什么不可预授权、影响哪些验收标准。

## 五 · 分级打断的可计算判据

```
剩余可推进条目 = 未变绿 且 不依赖任何挂起项 的条目数
剩余未完成条目 = 未变绿的条目总数

剩余可推进 / 剩余未完成 < 30%  →  功能转 BLOCKED，立即打断人类
否则                          →  静默记账，继续推进
```

**分母怎么数**：《测试目标清单》里状态非「绿」的全部条目（红、未开始都算）。已变绿的不算；被人类在确认阶段之后显式删除的条目不算。

**分子怎么数**：从分母集合里，剔除挂起清单「影响哪些测试目标条目」列所记编号的并集，剩下的就是分子。一条测试目标只要被任意一个未解除的挂起项点名，就不算可推进。

**什么时候重算**：

- 新增一个挂起项时（分子变小）；
- 一个条目变绿时（分子分母同时减一，比值可能因此下降）；
- 一个挂起项被解除时（分子变大，可从 `BLOCKED` 回到 `IN_PROGRESS`）。

三种事件都要重算——只在新增挂起时算会漏掉「越做越只剩边角料」的情形。

**边界情况**：分母为 0（全部变绿）时公式不适用，直接进最终验收。分母不为 0 而分子为 0 时比值为 0，必然打断。

**这条阈值防的是什么**：AI 看起来还在忙、实际只在干边角料，而主干早已被一个没人回答的问题卡死。

## 六 · 测试修改的两分法

执行期 AI 只被授权把《测试目标清单》变绿。清单本身能不能动，按下面两分：

| 类别 | 例子 | 动作 |
|---|---|---|
| **测试的实现细节** | mock 怎么搭、选择器怎么写、测试怎么拆合、fixture 数据怎么造、断言写法从 `toBe` 改 `toEqual` | 自主修改 → 追加决策日志 |
| **断言的业务语义** | 期望值改了、边界条件改了、该报错的改成不报错、把一条断言整个删掉 | **挂起** |
| **给清单新增一行** | 执行期发现确认阶段漏了一个验收面，想补一条测试目标 | **挂起**（见下）|

判据：改完之后，「这个功能对不对」的答案有没有可能改变？会 → 语义 → 挂起。不会 → 细节 → 自主改。

**验收标准两个方向都锁死：改一条是改验收标准，加一条同样是。** AI 不得自行给 `TEST_TARGETS.md` 新增条目，**哪怕新增的那条看起来明显应该有、明显是确认阶段漏了**——「明显该有」正是最容易被用来自我说服的措辞。两个理由：

1. 加一条测试目标就是扩了一次已批准的验收标准，而验收标准属「否」类，从来不可预授权。
2. **更隐蔽的一层：这张清单同时是第五节分级打断阈值的分母。** 允许自行加行，AI 就能往清单里塞几条容易变绿的条目，把 `剩余可推进 / 剩余未完成` 的比值抬回 30% 以上，于是本该打断人类的局面被粉饰成「还在正常推进」。这条路径不需要任何恶意就会发生——补漏动机本身就足以驱动它，而它恰好废掉了唯一那道「主干被卡死时叫醒人类」的判据。

正确动作：挂起该项，在挂起清单里写清「确认阶段漏了哪个验收面、不补会怎样」，交人类裁决是补进清单还是本轮不做。

**为什么这条重要**：确认阶段的理解偏差会变成一条错断言，执行期 AI 为让它变绿而写出错代码。这时唯一正确的动作是挂起并把矛盾报给人类，而不是「修正」断言让自己通过——后者等于 AI 自己改了验收标准。

## 七 · 自主模式不放宽的清单

自主模式改变的是「什么时候问人」，**不是「什么时候可以不验证」**。以下全部原样适用：

| 项 | 原样适用的内容 |
|---|---|
| 活路径验证标准 | 真实 UI / CLI / HTTP / DB 回读。读代码 + 绿单测不构成活路径证据。 |
| `PENDING_LIVE_VERIFY` 规则 | 缺活路径证据即进该状态；每一项推迟都是 `FEATURE_STATE.md` 里的具名 PENDING 行，不是报告里的一句叙述。挂起不能用来代替 PENDING 行。 |
| 实现边界 | 产品码与测试码交 `feature-developer` subagent；编排会话只做审查、验证、发布。**无人监督时更容易越界直改产品码，这条因此更紧而不是更松。** 唯一例外是子代理多轮零文件输出（目标目录没建、`list_agents` 一直 running）——此时降级为编排会话直接实现并留 `.impl-boundary-ack` 越界记录 + 独立评审必查（FB-20260814-005），这不是放宽边界，而是给无信号的等待一个有记录的出口。 |
| Loop 预算 | `LOOP_AND_SCOPE_POLICY.md` 的 Small/Standard/Complex 预算不变；耗尽即 `BLOCKED`。「自主模式所以多跑几轮」不成立。 |
| 发布门 | `ai-nseos-action-gate` 判据一字不改，它就是最终验收的机器执行点。 |
| Anti-patterns | 「为了让测试通过而删除/跳过/弱化测试」等全部照旧禁止。 |

## 八 · 回滚粒度

最终验收时人类可能否决某一个自决。因此自主模式要求**每个决策日志条目对应的改动可单独回滚**：

- 执行期强制小步提交，**一个决策一次提交**；
- commit message 引用决策日志条目号；
- 决策日志「可否单独回滚」列写「否」的条目，必须在写下它的当时就在报告里点名——因为那意味着人类在验收时只能全盘接受或全盘退回。

## 九 · 与说人话规则的关系

自主模式减少了提问次数，因此**每一次提问和最终验收呈报的质量权重更高**——人类只有这两三次机会理解 AI 做了什么。所有面向人类的文本一律适用 `HUMAN_COMMUNICATION.md`，验收呈报和挂起说明尤其适用。
