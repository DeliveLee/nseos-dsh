# Verification Integrity — 判真方法的唯一真源

> 本文件是「一项检查是否真的能区分好与坏」的**唯一** owner。其它 skill / agent / template 只许**指向**这里,不许复制其中的判据表和术语定义(`KNOWLEDGE_ENGINEERING.md` 的单一真源原则)。
> 引入版本:v0.25.0(批次 B)。

## 0. 这份文件要解决什么

AI-NSEOS 的流程约束已经很厚,**但「证据是否真的能区分好与坏」很薄**。系统很擅长要求提供证据,还不擅长验证证据本身。

三件真实发生过的事,本质是同一件:

| 实际检查了什么 | 本应证明什么 | 缺的判别力 |
|---|---|---|
| 评审脚本里某段失败文本是否出现 | 所有失败状态是否被识别 | 非零退出码、结构化结果、未知格式 |
| 手机端链接与 44px 类名存在于 DOM | 用户是否看得见、点得到、到达正确页面 | 计算后可见性、尺寸、遮挡、命中测试、真实点击与结果 |
| HTTP 状态码是 200 | 页面最终是否完整渲染且业务内容正确 | 完整响应、语义内容、错误壳、console / network |

共同形态叫**代理指标失真**:产品可以是坏的,代理指标仍然是绿的。

还有一类更隐蔽的,实测一轮抓到 12 条:**为了让用例变绿而削弱断言**。最典型是用**空权限身份**去断言「按钮不该出现」——该断言被权限门无条件满足,恒真、零判别力,而测试永远绿。

**本文件的核心问题只有一句:**

> 产品仍然是坏的时,这项检查是否还能保持绿色?

答不上来,这项检查就不算证据。

## 1. 五条命名空间(不得混用)

同一个 `BLOCKED` 过去同时充当验收结论、agent 执行状态、feature 阶段和 stop 决定,于是没有一处能被机器判读。分开:

```text
claim_verdict     PASS | FAIL | UNVERIFIED | NOT_APPLICABLE
execution_status  COMPLETE | PARTIAL | BLOCKED | NEEDS_INPUT
feature_phase     (生命周期值,见 `STATE_MODEL.md`)
reason_code       INVALID_TASK_PACKET | STALE_INPUT | NO_ORACLE | NO_NEGATIVE_CONTROL |
                  RUNTIME_MISMATCH | EVIDENCE_STALE | LIVE_PATH_UNAVAILABLE | ...
```

两条硬规则:

1. **`BLOCKED` 不是 claim 的结论。** 一条验收标准只能是 `PASS / FAIL / UNVERIFIED / NOT_APPLICABLE`。「我被挡住了」是 `execution_status`,不是「这条标准怎么样」。
2. **`execution_status` 与 `claim_verdict` 不可互相替代。** agent 跑完了(`COMPLETE`)不代表每条 claim 都 `PASS`;agent 中断了(`PARTIAL`)也不代表 claim 是 `FAIL`——没检查的就是 `UNVERIFIED`。

## 2. 证据级别 L0–L4

| 级别 | 含义 | 能否单独证明「用户可见的验收标准通过」 |
|---|---|---|
| L0 | 文件 / DOM 节点 / 类名 / 字符串**存在** | **否** |
| L1 | 静态规则、类型、结构检查通过 | **否** |
| L2 | 单元 / 集成测试在正常样本上通过 | **否** |
| L3 | **欺骗性反例能稳定让这项检查转红**(判别力证明) | 部分 |
| L4 | 真实运行环境里走通用户路径,且最终语义结果正确 | **否**(它证明真实路径,不证明判别力) |

**这不是「越高自动包含越低」的分数。** 每条 claim 用 `required_levels[]` 声明所需组合:

- **用户可见 + critical → 必须 L3 + L4。** 只有 L4 不够:一次手动点通了,不证明这项检查以后能抓住回归。只有 L3 也不够:测试能被改坏杀死,不证明真实用户路径可用。
- 纯内部逻辑 → 按风险取 L2 + L3。
- **L0 / L1 永远只能是辅助证据,不能作为最终 oracle。** 状态码 200、DOM 里有这个元素、源码里有这个类名——三者都在这一类。

## 3. 判别力四问(每条 critical / 用户可见 claim 必答)

写进 Review Report,不许留空,也不许写「已确认」:

1. **用户可观察的结果是什么?** 用产品语言写,不用实现语言。✗「`/api/orders` 返回 200」 ✓「用户点『提交订单』后看到订单号,刷新后订单还在」
2. **什么样的坏实现能骗过这项检查?**(failure model)至少写一条具体的。写不出来 = 你还不知道这项检查在测什么。
3. **判定 oracle 是什么、版本是什么?** 谁来裁决通过与否——一段断言、一个探针、一双眼睛?
4. **把那个坏实现真的做出来之后,检查转红了吗?**(negative control / mutation)

第 4 问没有实际做过,这条 claim 就是 `UNVERIFIED`,不是 `PASS`。

## 4. 变异验证(L3)怎么做才算数

**「命令变红」本身不等于变异被有效杀死。** 每条 mutation receipt 必须记全:

1. 变异**前** baseline 是绿的;
2. 补丁**成功应用**了;
3. 变异体**仍能编译 / 启动 / 到达目标路径**(否则你杀死的是语法错误,不是这条 claim);
4. 失败来自**这条 claim 的 oracle**,不是无关测试;
5. `KILLED / SURVIVED / INVALID / EQUIVALENT / TIMEOUT` **分开计数**;
6. 交替红绿 → `FLAKY` → 结论 `UNVERIFIED`,**不许挑一次绿的用**;
7. 还原之后再次通过。

**安全约束(不可协商):** 变异只能在**临时 clone / 临时 worktree / 复制出来的夹具**里做。**绝不允许**在有用户改动的工作树里用 `git reset` / `git checkout --` 之类「还原」——那会连人的未提交改动一起清掉。

**别把 mutation 摊到每一条检查上。** 只对 critical、用户可见、或使用了**新 oracle** 的检查要求本次 mutation;低风险检查可以引用一份已认证的 adapter receipt。把变异无差别铺开,这套制度自己就变成下一个成本放大器。

### 最低变异集(用户可见 UI claim)

| 人为破坏 | 正确结果 |
|---|---|
| `flex` → `hidden` | 可见性验证失败 |
| `display:none` / `visibility:hidden` / 透明 | 可见性验证失败 |
| `pointer-events:none` | 可点击验证失败 |
| 透明遮罩盖住按钮 | 命中测试或真实点击失败 |
| `href` 指向错误地址 | 导航结果失败 |
| 移除 click handler | 状态 / 业务结果失败 |
| 返回 200 但缺 title / H1 / 关键内容 | 页面语义验证失败 |
| 检查脚本换一种失败文本 + 非零退出码 | 仍必须判失败 |
| 复用上一个 HEAD 的截图 / 报告 | `EVIDENCE_STALE` |

## 5. 已知假绿形态 —— 必须能稳定转红

下面每一条都不是举例,是**实际发生过并造成返工**的形态。任何 reviewer 面对同类 claim 都必须按这里的判据核。

### 5.1 「元素在 DOM 里」≠「用户点得到」

**不足以判 PASS:** 元素存在、类名存在、`href` 正确、源码里有这段 markup。

**必须验:** ①浏览器**计算后**的可见性;②bounding box 非零(触控目标按项目标准,常见 44px);③中心点 `elementFromPoint` 命中目标或其合法子元素;④未禁用、未被遮挡、允许 pointer event;⑤执行**真实点击**;⑥点击后 URL / 页面状态 / 业务结果正确变化。

**禁止 `force click`。** 必须区分「初始视口可见」与「滚动后才可见」,并确认目标**唯一**——否则 locator 点到的是另一个同名可见元素,真正隐藏的那个漏检。

响应式不要只锁 `390×844`:由项目实际断点取 `断点-1 / 断点 / 断点+1`,必要时含横竖屏。`390×844` 只是其中一个常见样本。

### 5.2 「HTTP 200」≠「页面是对的」

响应头先发出去,后半段渲染失败,状态码仍然是 200。

**必须验:** 完整响应结束;title / H1 / 关键业务内容存在且正确;没有错误壳(error boundary / 500 页面 / 空状态被当成正常);无未处理异常、无关键请求失败、无非白名单 console error。

以下**任何一项单独出现都不算成功**:HTTP 200、DOM 里存在元素、源码里存在类名、HTML 体积非零、开发服务器页面正常、某字符串出现在不可见的源码里。

### 5.3 失败输出格式漏识别

判定脚本只认一种失败文本,换一种就静默判过。

**必须验:** 规范化的机器可读结果;**非零退出码本身即失败**;全部已知失败夹具都能被识别;**未知格式 fail closed**(判 `UNVERIFIED`,不判通过)。

命令型证据必须记录:`exit_code`、`signal`、`timed_out`、`output_truncated`、parser 版本、以及**期望退出语义**(`zero-means-pass` 还是别的)。这些相互矛盾时(例:结构化结果说 FAIL 但退出码 0)一律 `UNVERIFIED`。

### 5.4 断言恒真(实测一轮 12 条)

**红线:不许用空权限集 / 外部身份去断言「某元素不该出现」。** 权限门会无条件满足该断言,它恒真、零判别力,且永远绿。

**对照身份必须是「内部身份 + 精确缺某一个权限码」。** 同理:断言「列表为空」时,先证明在有数据的情况下这个断言会失败。

判断一条断言是否恒真的最快办法就是第 3 节第 4 问:**把实现改坏,它红吗?**

### 5.5 「代码支持」≠「产品可验收」 —— `CAPABILITY_ONLY`

代码里 HOME / CONTACT / PRODUCT / LANDING 四种展示位都实现了,真实数据里这四类**各有 0 条**。四个展示位一个都没被看见过,却被汇总成「已完成」。

**判据:** 枚举型展示面(placement / 类型 / 状态 / 角色)必须有**真实数据覆盖**才算验收通过。只有代码路径、没有任何一条真实记录走过它 → 结论是 `CAPABILITY_ONLY`,**不得汇总为产品通过**。

三条出路,选一条并写进报告:①造真实 fixture 或迁移真实数据后重验;②明确标注「本项依赖业务侧数据,验收暂缺」并列为 PENDING;③把该枚举值移出本次验收范围。**沉默地按「代码支持」计入通过**是这三条之外的第四种做法,它不被允许。

### 5.6 实现计划不是 oracle

**红线:reviewer 不得把实现计划、设计稿或开发者小结里的「已支持 / 已完成」当作事实输入。** 那是待验证的**声称**,不是真值。

实测形态(FB-20260728-004):计划写着「Dashboard 支持 SEO Schema 输出状态」,真实页面上根本没有这个字段;计划写着「私有页 noindex」,原始 HTML 里没有 robots noindex 且 canonical 错继承到首页。**测试是真绿的**,因为断言覆盖的是计划描述的代理指标,不是用户最终看到的结果。

**正确做法:从原始需求逐条重建可判定条目,再去找证据。** 需求 → 数据 → 接口 → 原始 HTML / 真实 DOM → 用户交互 → 最终终点,每一层都要有直接观察,不许中途换成代理。典型的中途换代理:重定向只验第一跳(真实链路 `/my-account/` → 301 → `/login/` → 307,「无重定向链」结论不成立)、SEO 只查渲染后 DOM 不查原始 HTML、后台字段只看 GraphQL schema 不看真实页面。

## 6. 证据的身份 —— 它说的是哪份代码、哪个运行物

只记 `head_sha` 不够。一份证据至少要能回答三层:

```yaml
candidate_code:    # 被审的是哪份代码
  repo_id: / base_sha: / head_sha:
  dirty: true|false          # 有未提交改动时,证据说的不是 head_sha 那份
runtime:           # 跑的是不是这份代码
  endpoint: / build_or_source_fingerprint: / config_profile: / fixture_or_dataset_id:
attestation:       # 谁用什么产生的
  runner_id_and_version: / oracle_id_and_version: / artifact_paths:
```

三条推论,直接可用:

1. **同一个 HEAD 下 staged / unstaged / 相关未跟踪文件变了,旧证据就失效。** 「HEAD 没变所以还算数」是错的。
2. **探针跑之前先确认 runtime 对应 candidate**:错端口、旧 build、旧 dev server、错数据库、错夹具、错身份 → `RUNTIME_MISMATCH` → `UNVERIFIED`,不是 `FAIL` 也不是 `PASS`。
3. **开发服务器不是发布 oracle。** Next.js 一类框架的 `dev` 服务器在并发压力下会写坏自己的构建产物:实测 6 并发的全站审计把 `.next/prerender-manifest.json` 写出重复尾部,随后 723/731 个 URL 统一返回 500;**同一份代码**用 `next build` + `next start` 的生产工件在同样 6 并发下 731/731 通过。**全站 / 压力 / 发布级验收必须针对已构建的生产工件执行**,dev server 上的同类结果判 `RUNTIME_MISMATCH` → `UNVERIFIED`,诊断时默认串行。同理,构建时环境身份必须进 `runtime` 记录(build-time env / start-time env / 端口 / 工作树 / 工件指纹):实测漏传一个 `NEXT_PUBLIC_STOREFRONT_URL` 导致图片优化器只允许错误端口,源图 200 而优化器 400,**旧标签与热缓存把它掩盖了**——媒体类验收必须包含冷缓存或等价负控。
4. **发布凭据已经机器化了这一层**:`.release-ready.json` 每字段带 `head_sha`,HEAD 一动即 `EVIDENCE_STALE`(v0.24.0)。写法与语义见 `INTEGRATION_AND_RELEASE.md` 步骤 2 —— **那里是凭据格式的唯一真源,不要在别处复制那条命令**。

## 7. 结构化纠错记录

发现自己先前的证据无效时,**不要写长篇自我辩解**。写这个:

```yaml
evidence_correction:
  previous_claim: "22 个分类页面均正常"
  invalid_evidence: "只检查了 HTTP 响应状态码"
  invalid_because: "流式渲染在发出 200 之后才失败"
  affected_scope: "22 个分类页面"
  replacement_oracle: "完整响应 + title/H1 + error-shell + console"
  result: FAIL
```

只说事实和影响。**主动纠错是健康行为,要鼓励;长篇复盘不是,它挤占的是修复的篇幅。**

## 8. 全量迁移 / 批量任务的验收 oracle

迁移类任务的假绿有自己的形状,和上面几类都不同——**跑完了 ≠ 跑全了**。

1. **必跑阶段要有机器可读的 phase manifest。** 实测:catalog 主迁移恢复了 395 个商品并报告成功,**受 guard 保护的 12 个子类目 backfill 整个没执行**,对应的落地页全空;单独补跑才恢复 262 条关联、187 个商品。**任一阶段未执行 = 整次迁移失败**,不能靠操作者记得再补跑脚本。
2. **长任务必须输出按对象 / 阶段的结构化进度,并在结束时做一次 reconciliation。** 「进程还在跑」不能证明健康。至少给 `phase`、`processed/total`、`last_object`、`last_progress_at`,并在 idle 超时后 **fail loud**——本次长时间无逐对象输出,「仍在工作」和「卡死」无法区分。
3. **集成测试必须记录数据源身份,并检查测试前后的业务不变量。** 默认强制一次性数据库:实测首次全套测试未显式传 DB 环境时落到了错误角色,而共享开发库上的测试在中断时留下了部分 category / facet 变更。**「测试过程断言通过」不够**——测试结束后商品数、关联数、类目结构这些不变量也要复核,避免测试绿、交付库坏。

## 9. 反过来说:什么时候不要上这套

这套东西本身有成本,滥用会变成新的摩擦源。**不要**:

- 对文案改动、纯格式化、注释、依赖版本号 bump 要求 mutation;
- 对每一条低风险断言写四问;
- 在没有 adapter、认证 / 种子数据不可得、或动作会污染真实数据时硬跑探针——那种情况正确答案是 `UNVERIFIED` + 说明原因,不是编一个;
- 把「真实路径」理解成「必须访问生产」。默认是本地 production-mode build 或用户已授权的安全环境;**禁止**为了拿证据去部署、去写生产数据。

**判据一句话:这条 claim 坏掉的时候,用户会不会真的受影响?** 会 → 上四问;不会 → L2 足够,把篇幅留给会的那些。
