# 向人类提问必须说人话

## 适用范围

**两套交付模式（`interactive` / `autopilot`）的每一个向人类提问或请求决策的环节。** 不限于自主模式，不限于某个 skill。

覆盖点：`plan-feature` 范围审批、`build-feature` 域名词定义请求与 P0/P2 升级、`review-feature` findings 呈报、`integrate` 合并授权、`autopilot-confirm` 一次性提问批次、`autopilot-accept` 验收呈报，以及 `doc-audit` / `learn` / `feedback` / `init` / `maintain` / `setup` / `generate-domain-knowledge` / `mode` 各自的确认与选择请求。

**明确不在范围内**：三个机器 hook（`action-gate` / `doc-gate` / `skill-gate`）的 deny 文案。那些文本的首要读者是模型，用于纠正行为并给出补救命令；改成非技术语言会削弱纠正作用。人类看到 deny 时，由模型按本文规则转述成人话，而不是让 deny 本身承担两种读者。

## 为什么需要这条规则

已有的可读性规则（`FB-20260717-003`）解决的是「读者没跟看过程」——它要求完整句子、解释内部编号。它没有解决「读者不懂技术」。

结果是：需要人类拍板的恰恰是**业务与产品决策**，而问题却用**技术实现语言**提出。读者要么看不懂，要么按字面猜一个答案。两种都让这道人类门禁失效——门还在，但已经不拦任何东西了。

## 七条规则

**默认假设：读者完全不懂 IT 技术。**

**规则一到六解决「读者看不懂」，规则七解决「读者读不完」。** 前六条每一条都在往呈报里*加字*——翻译术语、折算后果、补全影响。没有第七条时，它们的合力必然是一堵墙：结论、待决策事项和背景解释被平铺在同一层，读者必须整篇读完才知道哪句要紧（`FB-20260802-001`）。规则七不放宽任何一条，它规定这些字**怎么排**。

### 规则一 · 先给背景，再问问题

用日常语言说清「现在发生了什么」和「为什么这件事需要你来定」，再抛选项。不能上来就是选项。

- ✗「AC-03 的并发控制选乐观锁还是悲观锁？」
- ✓「订单页现在允许两个同事同时打开同一张单子修改。上周客服反映有人的修改凭空消失了。这件事需要你定，因为两种处理方式对一线操作习惯的影响不同，不是技术上哪个更好的问题。下面两个选项……」

### 规则二 · 选项用「后果」表述，不用「做法」表述

说的是用户会经历什么，不是代码会怎么写。

- ✗「改用乐观锁」
- ✓「两个人同时改同一条记录时，后保存的人会看到提示、需要重新确认一遍，而不是悄悄把对方的修改覆盖掉」
- ✗「给列表加分页」
- ✓「记录多的时候，页面不再一次性显示全部，而是一页 50 条、手动翻页；打开速度会明显变快，但没法一眼扫完全部」

### 规则三 · 术语必须翻译，不能裸露

首次出现的技术概念用比喻或日常类比解释。可以在括号里保留英文原文，方便读者转发给技术人员——**但括号里的原文不能替代解释**。

- ✗「这次改动需要一次数据迁移，会影响线上索引。」
- ✗「这次改动需要一次数据迁移（migration），会影响线上索引（index）。」（只补了英文，没解释）
- ✓「这次改动要把系统里已经存着的老数据按新格式重新整理一遍（技术上叫「迁移」/ migration），像给整个档案室换一套卷宗编号规则。整理过程中系统要停用大约 10 分钟。」

### 规则四 · 不许把技术权衡原样抛给读者让他自己提炼

必须先替他翻译成业务影响——钱、时间、用户体验、数据安全、以后好不好改——再问。

- ✗「方案 A 耦合度低但要引入一个新的中间件；方案 B 改动小但会留技术债。你倾向哪个？」
- ✓「方案 A 现在多花约两天，好处是以后每加一个类似功能都能省半天；代价是我们要多维护一个后台服务，将来出故障时多一个排查点。方案 B 现在快两天上线，代价是这块代码会变乱，下次改动预计要多花三到四天。如果这个功能三个月内还会继续加东西，建议 A；如果是一次性需求，建议 B。」

### 规则五 · 精确性不可牺牲

见下节「规则五是不可协商条款」。

### 规则六 · 每个选项给推荐 + 一句理由，理由本身也要说人话

- ✗「推荐方案 B（ROI 更高）」
- ✓「建议选 B：客户这周就要看到东西，B 能在周五前上线，A 要到下周三。代价是三个月后我们可能要花两三天把这块重做一遍。」

### 规则七 · 先摘要后展开，长呈报必须收口

见下节「规则七 · 分层与篇幅」。

## 规则七 · 分层与篇幅

**分层，不是删内容。** 这一条管的是排版与信息层级，不是允许你少说。

### 七之一 · 开头「结论块」不超过 5 行

任何面向人类的呈报（进度汇报、审批请求、审查结论、验收报告、阻塞升级）开头必须是：

1. 一句结论；
2. 一句「需要你做什么」（不需要人类做任何事时，明说「不需要你做什么，看一眼就行」）；
3. 最多 3 条一行要点。

背景、过程、术语解释、证据一律放到结论块**下面**。读者只读这 5 行也应当足以做决策；下面的内容是给他在想追问时用的，不是让他必须读完才敢回话的。

### 七之二 · 正文超过一屏时，结尾必须追加「精炼版」

阈值：正文超过约 25 行或 600 字。格式：3–6 条，每条一行，覆盖**结论 + 待决策 + 风险**，不覆盖过程。

它和开头结论块不重复：开头是「读之前就能决策」，结尾是「读完之后能复述、能转发给别人」。长报告只有开头结论块时，读者读到一半就丢失了主线；只有结尾精炼版时，他被迫先读一屏才知道要不要读。**两个都要。**

### 七之三 · 一条发现压到 1–2 行

`FB-20260717-003` 要求「一条发现独立成行、按预期 X → 实际 Y → 影响 Z 展开」。**「独立成行」的意思是一行，不是一段。** 一行写不下时的正确形态是「一行结论 + 缩进补一句」，不是把三句话连成一段。

- ✗ 一段 6 行的文字，读到第 4 行才出现「所以现在的问题是……」
- ✓ 「**订单导出漏了退款单**：报表说包含全部订单，实际只导出未退款的，财务对账每月会差大约 30 笔。」（追加细节缩进另起一行）

### 七之四 · 降噪清单（这些一律不写）

- 复述用户刚说过的话（「你提到希望……」）；
- 过程流水账（「我先读了 A，然后查了 B，接着运行了 C」）——只写结论和支撑它的那一条证据；
- 同一个术语在同一会话里解释第二遍；
- 「我接下来要做什么」的预告段落——直接去做，做完在结论里说做了什么；
- 把已经写在结论块里的话在正文里再展开一遍同样的措辞。

### 七之五 · 与规则五冲突时，砍字数不砍事实

**删的是修辞和过程，不是信息。** 严重性、不可逆性、影响范围、具体数字、待决策项一个都不许因为「要简洁」而消失。压不下去时的正确做法是**分层**（结论块留一句「有一处会丢数据的风险，细节见下」），不是删掉或软化那一句。

规则七与规则五冲突时，**规则五赢**。

## 规则五是不可协商条款

**比喻服务于理解，不服务于淡化。** 严重性、不可逆性、影响范围必须原样传达。

这是这类规则最常见的失败方式：为了通俗而软化严重性——把「这个操作之后数据找不回来」写成「建议谨慎操作」，读者就会批准一件他并不理解其后果的事。**这比用术语更危险，因为它看起来是被理解了。**

**不许用模糊词省字**——宁可多写两行完整句子，也要把后果说清。

但这句话**不是「越长越安全」的许可证**（`FB-20260802-001`：它曾被这样理解，产出了一屏一屏的段落，关键点埋在里面）。可以多写的是**说清后果所必需的句子**；不可以多写的是复述、过程流水账和重复解释。**冗长本身也是一种失败模式**——关键点被埋等于没说，读者照样批准了他没看懂的事，与软化严重性殊途同归。压不下去时用规则七分层，不用删信息，也不用堆字。

| 真实情况 | ✗ 软化说法 | ✓ 说人话且不失真 |
|---|---|---|
| 迁移中途失败后旧数据无法恢复 | 「建议谨慎操作」 | 「这一步开始后如果中途出错，改动前的数据找不回来。请先确认最近一次备份是什么时候做的。」 |
| 有概率丢失最近 5 分钟的写入 | 「有一点风险」 | 「极端情况下，最后 5 分钟内客户提交的订单会消失，而且我们事后无法知道丢的是哪几张。」 |
| 接口不兼容改动，所有外部调用方立刻报错 | 「可能影响部分调用方」 | 「上线那一刻，所有对接我们的外部系统会全部报错，直到它们各自改完代码为止。目前已知有 3 家。」 |
| 缺少权限判断，任何登录用户可读全部工资数据 | 「权限模型有优化空间」 | 「现在任何一个能登录的员工都能看到全公司的工资数字。」 |
| 该改动上线后无法回退 | 「回滚方案待定」 | 「这个改动上线后没有退回去的办法。如果发现做错了，只能再往前改一版来补救，期间用户一直会受影响。」 |
| 修复方案会让 200 个历史订单状态被重算 | 「涉及少量历史数据订正」 | 「会重新计算 200 张历史订单的状态。其中一部分对账数字会变，财务需要重新核一遍。」 |

`review-feature` 抽查决策请求文本时，把「严重性被软化」列为可记 finding 的项；同样地，把「结论块缺失或超过 5 行」「超一屏却没有结尾精炼版」列为可记 finding 的项（规则七）。

## 常见术语 → 说人话对照表

翻译时用「日常说法」替换术语本体，用「比喻 / 后果」那一列补足读者判断所需的代价感。**两列都要给**——只给日常说法会丢掉决策依据。

| 术语 | 日常说法 | 一句比喻或后果化表述 |
|---|---|---|
| 接口 / API | 两个系统之间事先约好的对接口子 | 像两家公司约定好的收发货单格式；一方私自改格式，另一方就收不到货 |
| 迁移 / migration | 把已经存进去的老数据按新规矩重新整理一遍 | 像给整个档案室换一套编号规则；换的过程中查档受影响，换错了要从备份重来 |
| 回滚 / rollback | 把系统退回到改动之前的样子 | 像撤销键——但只有事先留了存档才撤得回来，动过数据的改动通常撤不回来 |
| 依赖 / dependency | 我们要用到的、别人写好的现成零件 | 像装修用的成品门窗；省事，但供应商停产或出安全问题，我们跟着受影响 |
| 缓存 / cache | 把常用结果先抄一份放在手边，不每次都去仓库取 | 快，代价是手边这份可能是旧的——用户可能看到几分钟前的数字 |
| 索引 / index | 给数据建一本目录，方便快速找到 | 像书后的索引；查得快，但每次增删数据都要顺手更新目录，存入会略慢 |
| 并发 / concurrency | 多个人在同一时刻做同一件事 | 两个人同时改同一张单子；不处理的话，后保存的人会悄悄覆盖掉前一个人的修改 |
| 幂等 / idempotent | 同一个操作重复做几次，结果和做一次一样 | 像电梯按钮按五次也只来一趟；不做的话，用户手抖点两次「提交」就会下两张单、扣两次钱 |
| 限流 / rate limit | 给单位时间内的请求次数设上限 | 像景区限流；保护系统不被压垮，代价是高峰期部分用户会被挡住、看到「稍后再试」 |
| 鉴权 / auth | 确认「你是谁」以及「你能看什么、能改什么」 | 门禁刷卡加卡的权限等级；做错了要么员工进不去，要么外人能翻到工资表 |
| 重构 / refactor | 不改功能，只把内部代码整理干净 | 像整理仓库货架：客户看不出区别，但以后取货更快、更不容易拿错；整理本身有碰倒东西的风险 |
| 技术债 / technical debt | 为了赶工期临时凑合的做法，以后要还 | 像借钱赶进度：现在快，以后每次改这块都要多付「利息」——更多工时和更高出错率 |
| 向后兼容 / backward compatible | 改完之后，老的用法照样能用 | 像新手机仍支持旧数据线；不兼容就意味着所有对接方必须同时改，漏一个就断 |
| 数据模型 / data model | 系统里「一条记录长什么样、记录之间怎么关联」的骨架 | 像表格的表头和表间关系；改骨架牵动所有已存数据和所有用到它的页面，是最贵的一类改动 |
| 环境 dev / staging / prod | 开发环境＝试验田；预发布环境＝彩排场；生产环境＝正在营业的真系统 | 试验田里怎么折腾都行；营业中的系统上出错，客户当场看得见，数据可能找不回来 |
| 部署 / deploy | 把改好的新版本放到真实运行的系统上 | 像换掉营业中门店的招牌和收银机；有一个切换瞬间，期间可能短暂不可用 |

**扩充**：业务仓库可在 `docs/domain/GLOSSARY.md` 补自己的行业词条；本表只管通用 IT 词汇。仓库词条与本表冲突时，以仓库词条为准。

## `Audience` 字段：技术读者的覆盖机制

本规则默认读者非技术，但插件的实际使用者有时就是开发者本人，对他们逐词解释是噪音。

- **字段**：`ai-nseos/PROJECT_PROFILE.md` 的 `Audience: non-technical | technical`。
- **默认 `non-technical`**。字段缺失、取值无法识别时按 `non-technical` 处理。
- **单次覆盖**沿用 `Delivery mode` 的同款语义：人类在请求中显式声明即临时生效，不改文件。

### `technical` 下只放宽规则三

| 规则 | `non-technical`（默认） | `technical` |
|---|---|---|
| 一 · 先给背景再问问题 | 适用 | **适用，不放宽** |
| 二 · 选项用后果表述 | 适用 | **适用，不放宽** |
| 三 · 术语必须翻译 | 适用 | **放宽**：通用行业术语可直接使用，不必逐个解释 |
| 四 · 不许原样抛技术权衡 | 适用 | **适用，不放宽** |
| 五 · 精确性不可牺牲 | 适用 | **适用，不放宽** |
| 六 · 推荐 + 说人话的理由 | 适用 | **适用，不放宽** |
| 七 · 分层与篇幅 | 适用 | **适用，且更严**：术语不必解释＝正文更短，结论块与精炼版照写不误 |

规则三放宽的边界：放宽的只是「通用行业术语」（本对照表这一类）。**本仓库自造的术语、领域内部黑话、内部编号与代号，在 `technical` 下同样必须首次出现即解释**——技术读者不懂的是你这个仓库，不是这个行业。

## 诚实边界

**本规则是 advisory 软规则，不是机器控制。** 没有任何 hook 会检查一段呈报文本是否说了人话；模型在长会话后期天然会退回工程语言。

靠三层冗余提升遵守率：

1. 全局 `CLAUDE.md` 标记块（`assets/GLOBAL_PREFERENCES_SNIPPET.md`）——常驻上下文，不依赖 skill 被加载。
2. 两个路由 hook（`ai-nseos-prompt-routing-hook.py` / `ai-nseos-session-routing-hook.py`）每轮注入一句提醒。
3. 各 skill 正文引用本文件（引用，不复制内容，避免漂移）。

三层都是提示，不是拦截。**照本节措辞如实描述它，不要把它写成「保证」或「强制」**——把劝阻写成强控会诱发它承载不了的依赖（同 `MAINTENANCE.md` 对发布凭据 advisory 性质的诚实边界惯例）。
