# 自主交付模式(autopilot)

本技能把自主模式拆成两段:第一段「confirm」把执行段不打扰人类所依据的全部合同落盘,第三段「accept」把执行段无人监督期间发生的一切向人类结账(第二段实施在 `nseos-build-feature`,不在本技能)。

**autopilot 只改「何时问人」,不改任何判据**:门禁判据、证据标准、实现边界、loop 预算与 `interactive` 完全一致;任何不可判读的情形一律回退 `interactive`(回落方向永远取「多问人几次」那一侧)。

## 第一段:需求确认(confirm)

本段产出的不是「计划」,而是**执行段不打扰人类所依据的全部合同**。它成立与否,决定了第二段能不能真的走完。三步:勘探(问代码)→ 提问(问人,一次)→ 固化(写合同)。术语门也在这一段清完。

0. **标记流程激活(flow marker),让机器 skill-gate 放行你在本流程内调用的步骤内技能。** 用 `write` 工具写单行 JSON 到 `<仓库根>/ai-nseos/state/flow/<session-slug>.json`(结构契约见 `FLOW_MARKER_CONTRACT.md`):`{"session_id":"<本会话 id>","started_at":"<ISO8601 UTC>","mode":"autopilot-confirm","contract":"<一行合同要点>"}`。`session_id` 取本会话 id,勿猜、勿留占位符——门禁据此归属 marker;`contract` 一行要点(单行、不含双引号);`<session-slug>` = session_id 的非法字符替换、拒绝 `..`。marker 一会话一文件,写仓库根;DSH 无 worktree,「主检出 / 共享 worktree」语义不适用。长流程跨小时要重写同一文件、`started_at` 重新生成。两点补充:(a) 勘探与 spike 常常真的跑上几小时,重写不是形式话——marker 过期(>4h)会让后续步骤被 skill-gate 拦下。(b) **若本次是单次覆盖进入自主模式**(仓库 `Delivery mode` 仍是 `interactive`,人类在本轮显式指名要自主模式,见 Step 1),这次「按哪套交付模式办」必须留痕两处:其一,给 marker JSON 加一个可选字段 `"delivery_mode":"autopilot"`(仓库设置本身就是 `autopilot` 时不必加;需要临时压回协作模式就写 `"delivery_mode":"interactive"`);其二,同样写进 `FEATURE_CONTRACT.md`(轻量模式则写进会话里的合同要点)一句「本次为单次覆盖,按 `autopilot` 执行;仓库设置仍是 `interactive`」。`delivery_mode` 与 `mode` 不是一回事:`mode` 记流程阶段,`delivery_mode` 记这次按哪套办;门禁两者都不校验,也不会因为多了未知字段而拒绝,纯粹留痕。**重写 marker 时这个字段不会自己留下来**——刷新时只有 `goal_source` 会被自动携带,`delivery_mode` 要一并重写,否则字段就没了。
1. **模式判定,不合就停。** 读当前 workspace 的 `ai-nseos/PROJECT_PROFILE.md` 的 `## Delivery settings` 节里的 `Delivery mode` 字段;读不到、没有该字段或取值不认识,一律当作 `interactive`(回落方向永远取「多问人几次」那一侧)。若它不是 `autopilot`,并且人类在本次请求里没有**显式指名**要用自主模式(例如「这次用自主模式」「这次自己跑完再叫我」),就**停下来解释**。这段解释按 `references/HUMAN_COMMUNICATION.md` 的七条规则写——它是本技能里唯一可能发生在 Step 3 读真源之前的对人环节,所以真要停在这里,**先把那份 reference 读了再开口**。写的时候记住对方的处境:他只是提了个需求,突然被告知「这个仓库不是这个模式」,他多半不知道自己踩到了什么,也不该被要求先理解一个字段名。**不要写「`Delivery mode` 字段当前为 `interactive`,本技能需要 `autopilot`」这种话**——那是把一个内部开关的名字丢给他,不是解释。要讲清三件事,都用他会经历什么来说:
   - **现在会怎么给他干活**:我接下来会一边做一边问你,每碰到一个需要你拿主意的地方就停下来等你回答;好处是你随时能改主意、随时喊停。
   - **这和他可能期待的差在哪**:如果你本来是想交代完就去忙别的,那这种方式会让你失望——我会停在第一个问题上等你,你不回来我就一直等着,看起来像卡住了。另一种方式是我先花更多时间把该问的一次性问完、写成书面约定,之后你可以走开,代价是前期这段确认要占整件事三到五成的时间。
   - **想换该怎么做**:换成长期的,改 `ai-nseos/PROJECT_PROFILE.md` 的 `Delivery mode` 字段(写进仓库设置,对之后所有人生效);只想这一次这样,在请求里直接说一句「这次用自主模式」就行,仓库设置不动。
   然后给出推荐并说明理由:**默认建议改用 `nseos-plan-feature` 接着往下走**,因为那是这个仓库现在设定的方式,而且不需要先花那三到五成时间做前期确认。同时如实说明:两种方式在「该验的证据、该你批的发布」上完全一样严,区别只是我什么时候打断你——不要让他以为换模式能让事情变松。**「你直接做就行」「别老问我」不算覆盖**——那是对这次任务的不耐烦,不是要交出执行期全部打断点的决定,不要因为「用户看起来很忙」就自行推断。反过来,若人类确实显式覆盖了仓库设置,那是**单次覆盖**:照常继续,但要留两处痕迹——Step 0 那条 marker JSON 加上 `"delivery_mode":"autopilot"`,`FEATURE_CONTRACT.md` 里写一句「本次为单次覆盖,按 `autopilot` 执行;仓库设置仍是 `interactive`」——并且**不改 `PROJECT_PROFILE.md`**。
2. **未 init 先 init。** `ai-nseos/PROJECT_PROFILE.md` 缺失或仍是 UNINITIALIZED 时,先初始化它(幂等、低风险、不碰业务码、不提交),再回到这里继续——不要让用户手动去调。
3. **读真源。** 读 preset 内 `references/AUTONOMY_POLICY.md`——自主模式的唯一真源,本技能只负责把它落成文件,不重新定义它:第一节「不打扰 ≠ 不阻塞」、第二节红线、第三节拿到预授权级别后执行期怎么用、第四节挂起(PARKED item)语义、第五节分级打断阈值(可计算判据)、第六节测试修改两分法、第七节不放宽清单、第八节回滚粒度。**预授权级别本身怎么判,真源在 `references/AUTHORITY.md` 决策矩阵第 4 列「可否预授权(autopilot)」,不在 `AUTONOMY_POLICY.md`**——本技能凡涉及判级一律查那一列。再读 `references/HUMAN_COMMUNICATION.md`——**本技能里每一处向人类说话的地方,一律按它的七条规则书写,没有例外**。这是全覆盖的要求,不是一张清单:Step 1 的「模式不对、停下来解释」、Step 8 的勘探报告、Step 9 的提问批次、Step 15 的批准请求都在内,任何本文没预见到的临时说明也在内。**不要把这个引用理解成「只有被点名的那几步才适用」**——排除式的作用域正是漏掉对人环节的典型原因。其余读 `references/FEATURE_LIFECYCLE.md`、`references/LOOP_AND_SCOPE_POLICY.md`、`references/AUTHORITY.md`、`references/STATE_MODEL.md`、`references/SECURITY.md` 和四份自主模式模板(`templates/RECON_REPORT.md`、`templates/TEST_TARGETS.md`、`templates/DELEGATION_MATRIX.md`、`templates/DECISION_LOG.md`)。
4. **建 feature 目录,并守住实现边界。** 分配/确认项目内唯一的 Feature ID,从 preset 模板建 `ai-nseos/state/features/<feature-id>/` 六件套,状态先置 `DISCOVERY`。**自主模式一律走 full mode,没有 lightweight 分支**——轻量模式省下的纸面工作,正是执行段不打扰人类的唯一依据,省掉它等于把自主模式变成无合同的放任。本段除 Step 6 的可抛弃 spike 外**不修改任何业务代码**。
5. **勘探:按维度实派只读 subagent(问代码,不问人)。** 这一步必须**真的派出去**,不允许在编排会话里内联做完再声称派过(FB-20260719-004:说了要派 product-analyst/architect 却在主会话里顺手做掉,等于放弃了第二个独立视角)。四个维度,各挖一遍并保留各自输出(用 DSH `subagent` 工具,给各角色对应 prompt):
   - `product-analyst` —— 产品缺口、用户路径、边界与空态。
   - `architect` —— 依赖、耦合、接口影响、迁移与回滚风险。
   - `domain-knowledge` —— 本功能触及的**全部**域名词,逐个对照 `docs/domain/GLOSSARY.md`(这一份直接喂给 Step 13 的术语门)。
   - `security-reviewer` —— 信任边界、权限、数据暴露;当功能触及认证、真实数据或外部输入时必派。
6. **可抛弃 spike:把「不可预知」主动转成「已知」。** 对勘探判定为高不确定的点,允许写、跑、然后**删掉**一次性验证代码——起服务打真实接口、建临时测试探耦合、拿真实数据样本跑一遍。约束三条:(a) spike 代码一律写在 `ai-nseos/state/features/<feature-id>/spike/` 下,不散落进业务目录;(b) **代码不入库**,本步结束前删除该目录并用 `git status` 确认工作树干净;(c) 每个 spike 在勘探报告的「可抛弃 spike」表里占一行(`S-xx`:想验证什么、怎么做的、结论、结论落到哪条 `F-xx`/`U-xx`、产物是否已清理),并在该节的「收尾检查」栏贴上 `git status` 输出摘要作为清理证据——没写进报告的 spike 等于白跑,删干净但结论丢失是这一步最常见的浪费。spike 仍受生产/密钥红线约束:它是只读验证手段,不是绕过 `references/SECURITY.md` 的口子。
7. **产出《勘探报告》** `ai-nseos/state/features/<feature-id>/RECON_REPORT.md`(从 preset `templates/RECON_REPORT.md` 建)。模板已定好结构,照填即可,但两张主表的判据要守住:
   - **已验证事实(编号 `F-xx`)** —— 只写跑过、看过、有输出的结论,证据类型限模板列出的六种(命令输出 / HTTP 响应 / 测试结果 / DB 回读 / 代码位置 / UI 观察)。「读了代码觉得是这样」记 `代码位置`,且措辞不得超出代码能证明的范围;推断一律不进这张表,进下一张。
   - **未验证疑点(编号 `U-xx`)** —— 每条附「为什么没验」「撞上了会怎样」和按 `references/AUTHORITY.md` 决策矩阵第 4 列判出的「可否预授权」;**拿不准这条疑点落在哪一类时,按「否」填**——挂起的成本是一条边角料没做,误判成「可」的成本是一次没人知道的自决。**这张表逐条决定 Step 11 授权书的条目**,授权书不得有这张表之外的来源,所以它宁可长、不可漏。
   - 模板还要求填「勘探方法记录」(四个维度是否真的派了、未派要写原因)、「可抛弃 spike」表(含产物是否已清理)、「域名词清点」表(喂给 Step 13)和「勘探的自评」(哪里可能还漏)。自评那一节不是客套——说清盲区比装完整有用得多。
8. **强制交付节点:勘探报告先给人类过目,再进提问。** 确认阶段最容易变成一个跑几小时、人类看不见任何东西的黑箱,体验比协作模式更糟,所以这里必须断开成两次交互。按 `references/HUMAN_COMMUNICATION.md` 写这份呈报:默认读者完全不懂 IT 技术——先用日常语言说清「我去看了什么、看出了什么」,发现用**后果**表述而不是做法表述,术语首次出现即翻译(可在括号里保留英文原文方便转发,但括号不能替代解释),严重性与不可逆性原样传达、不许为了通俗而软化(把「这个改动之后数据找不回来」写成「建议谨慎」比用术语更危险,因为它看起来像是被理解了)。呈交后等人类回应再进 Step 9;人类说「继续」即可,不需要逐条批注。
9. **提问:一次性问完,然后封口。** 只提**代码回答不了、只有人类知道**的问题:业务规则与阈值、优先级、冲突时先保谁、术语的业务定义、`LOOP_AND_SCOPE_POLICY.md` 里 Expected 类范围项要不要纳入。全部问题集中成**一批**呈交,按 `references/HUMAN_COMMUNICATION.md` 七条书写,并沿用给不在场读者写字的老规矩(FB-20260717-003):每个问题独立成行的完整句子、各带一个推荐选项和一句说人话的理由、内部编号与标签首次出现即解释,不许把多个问题塞进一段分号串联的话。**再叠加规则七(分层与篇幅,`FB-20260802-001`)**:开头 5 行内给「一句结论 + 需要你做什么 + 最多 3 条一行要点」,背景与证据放它下面;正文超过一屏(约 25 行)时结尾追加 3–6 条一行的「精炼版」(结论 + 待决策 + 风险);一条发现压到 1–2 行而不是一段。**砍的是修辞和过程,不是信息**——严重性、不可逆性、影响范围、数字与待决策项一个都不许因为求简而消失,与「精确性不可牺牲」冲突时后者赢,压不下去就分层。这一批问题是人类在整段自主执行前唯一一次开口的机会,**问题清单本身要能一眼扫完**——扫不完的清单会被囫囵回答,和没问一样。**问完封口**——从进入第二段起不再提问,所以「想到再问」在这里就是漏问。把答案逐条记进 `DECISION_LOG.md` 的来源栏与 Feature Contract。
10. **固化之一:《测试目标清单》** `TEST_TARGETS.md`(从 preset `templates/TEST_TARGETS.md` 建)。把每条已批准验收标准展开成具体测试条目(编号 `T-xx`):对应的 AC 编号 + 测试文件路径 + 测试名 + **断言的业务语义** + 状态(只有红/绿两种,「部分通过」「跳过」「本地绿 CI 未跑」都记红)。**没有任何 `T-` 行的 AC 不允许存在**——那意味着这条验收标准在执行期无人负责。它有三重身份,写的时候三个都要成立:
    - **执行期的授权边界** —— 执行段 AI 被授权做的事就是「把这张清单变绿」,清单之外的行为改动即超出合同、必须挂起。
    - **最终验收的对照表** —— 第三段逐条从红变绿并附运行输出。
    - **分级打断阈值的分母** —— 表写得糙,阈值就算得不准,主干被卡死时不会有人被叫醒。
    因此**宁可条目多而具体,不要少而笼统**;一条笼统条目会在执行段变成一片没人管的灰色地带。另外要在文件里写死一条:**执行期不得给本表新增行。** 执行期发现遗漏的验收面时,写进挂起清单等人类裁决——自己加一行再自己把它变绿,等于 AI 自己扩了验收标准,而人类会以为清单还是他批准的那份。
11. **固化之二:《授权书》** `DELEGATION_MATRIX.md`(从 preset `templates/DELEGATION_MATRIX.md` 建)。对 Step 7「未验证疑点」表里的**每一条**,事先约定撞上了怎么处置:授权条目 `A-xx` → 对应疑点编号 `U-xx` → 若成真的表现 → 默认处置 → 可否回滚 → 人类逐条签署。四条硬约束:
    - **只列勘探实际识别出的疑点,禁止用通用风险清单填充。** 每一行的 `U-xx` 必须能在 `RECON_REPORT.md` 里查到同号条目,查不到就删掉这行。人类面对一屏「遇到 X 怎么办」会疲劳并全选默认,授权书就退化成橡皮图章,自主模式随之失去全部安全边际。同理,**整表一次性「全部同意」不构成有效授权**——要逐条签。
    - **红线节不可删除、不可协商**(模板内置,是 `AUTONOMY_POLICY.md` 第二节的副本):门禁凭据(`ai-nseos/state/.release-ready.json` 的 `review` / `prod_schema` / `doc` 三字段)永远不可预授权、不可自签充数;门禁阀门(机器层门禁的逃生舱)属**人类运维**,模型既不得自行关闭,也不得为跳过没做完的工作而请求关闭(逃生舱见 `DECISIONS.md` D5#10,人类运维、模型不得自关)。撞到门禁是**合法挂起**,不是失败。这一节存在的理由有实测:一个长跑会话在反复回压下两次正确拒绝门禁,第三次执行了关闭门禁阀门的命令(FB-20260725-003);「执行期不许打扰用户」正是同一种压力的制度化版本,模型会把「不能问人」误读成「必须自己想办法通过」。
    - **判为「否」的疑点不进授权表,进模板的「明确不授权(挂起清单预置项)」节**(编号 `N-xx`),执行期撞上即直接挂起、不需再判断。**判级的唯一真源是 `references/AUTHORITY.md` 决策矩阵的第 4 列「可否预授权(autopilot)」**,照它判,不要现场发明标准;拿到级别之后执行期该做什么动作,见 `references/AUTONOMY_POLICY.md` 第三节。判为**「有限可」**的疑点可以进授权表,但默认处置里必须把真源标注的**方向写死**(如「仅限不破坏兼容的改法」「仅限白名单内的依赖」)——**越出该方向与「否」类同样是挂起来源**,方向写得含糊,执行期就会把越界当成普通自决记进决策日志。若勘探识别出可能要新增外部依赖,填「预授权白名单」节并写明名单外一律挂起;不适用就整节删掉。
    - 每条的「可否回滚」不是形容词,要写清回滚动作(单条 commit 回退 / 配置开关 / …);写「否」的条目在签署时应默认倾向拒绝并改为挂起。它是第三段人类否决某个自决时的唯一退路。签署节还要人类明确「类推自决:允许 / 不允许」——那是授权书没覆盖时的兜底口子,开不开由人类定。
12. **固化之三:《决策日志》** `DECISION_LOG.md`(从 preset `templates/DECISION_LOG.md` 建),本段建成**两张空表**加一张空的门禁挂起记录表:表一是决策日志(`D-xx`:时间、触发情形、依据的授权条目、实际选择、影响文件、对应 commit、可否单独回滚);表二是挂起清单(`P-xx`:时间、撞到什么、为什么不可预授权、影响哪些 `T-xx`、是否阻塞主干、解除情况)。三件事要在建表时就写死在文件里:
    - **一个决策一次提交,commit message 引用决策日志条目号**——多个决策挤进一次提交,人类在第三段就只能全盘接受或全盘退回。
    - **表二「影响哪些测试目标条目」必填**,它与 `TEST_TARGETS.md` 的「是否被挂起项阻塞」列互为镜像;漏填会让分级打断的阈值算偏,主干卡死时无人被叫醒。
    - **挂起不能代替 `PENDING_LIVE_VERIFY`。** 缺活路径证据是完全另一回事:它照旧走 `FEATURE_STATE.md` 里的具名 PENDING 行,不许记成挂起项来蹭「不阻塞主干、可以跳过去做别的」这个待遇。把「没验」写成「被挂起」,等于用一个流程概念把一条没兑现的证据义务藏起来。
13. **术语门在本段清完。** 以勘探报告「域名词清点」表为清单(每个名词标了「已定义 / 未定义 / 标记歧义」),把本功能触及的全部域名词一次性定义完写进 `docs/domain/GLOSSARY.md`;需要业务方确认才能定的,登记进 `docs/domain/OPEN-QUESTIONS.md` 并在提问批次里问掉,不要留到执行期。全部清空后,写 `ai-nseos/state/features/<feature-id>/.gate-armed`(用 `write` 工具,空文件即可)武装术语门,再写 `ai-nseos/state/features/<feature-id>/ambiguity-cleared`。**两个文件都要写**:只写 `ambiguity-cleared` 而不武装,等于机器门禁从未生效(实测 bonohair-rebuild 9 个功能里 5 个没武装,术语澄清被静默跳过,FB-20260720-001)。顺序摆对之后,`doc-gate`(文档门禁)在执行段自然不会再触发——因为已经没有未定义的术语了。这是顺序问题,不是把门禁关掉。若该仓库尚未采用文档体系(没有 `docs/domain/`),在 Feature State 里写一行说明本步不适用,而不是让标记单纯缺席。
14. **汇总进合同并更新索引。** 在 `FEATURE_CONTRACT.md` 里记录目标、非目标、Required/Expected/Optional/Out-of-scope 分类、允许与禁止路径、依赖、风险、验收标准、所需证据、loop 预算、审批人,并把 `RECON_REPORT.md` / `TEST_TARGETS.md` / `DELEGATION_MATRIX.md` / `DECISION_LOG.md` 四份文件挂为合同附件;`IMPLEMENTATION_PLAN.md` 写成小步可回退的计划(小步的粒度对齐 Step 12 的「一决策一提交」);更新项目的 Feature Index。
15. **状态设 `AWAITING_APPROVAL`,呈交批准请求。** 只呈交需要人类拍板的产品、架构、安全与成本决策,以及**授权书本身**——批准范围的同时就是在批准「哪些事以后由 AI 替你决定」,这一点必须在请求里明说,不能夹带通过。整份请求按 `references/HUMAN_COMMUNICATION.md` 书写,并给出一句诚实的成本预期:自主模式的确认阶段约占整体工时的 30–50%,换来的是执行段只在跌破阻塞阈值时才打断。

Stop. 只有人类的批准把状态改成 `APPROVED` 之后,才进入第二段实施(`nseos-build-feature`)。**`DELEGATION_MATRIX.md` 这个文件存在与否,本身就是 build-feature 走不走授权书分支的开关**:文件在,它就把原本要停下来问人的地方改为查授权书;文件不在,它按协作模式原样运行。所以本段没把授权书真正落盘,第二段不会自动变成自主模式——它只会像平常一样跑,然后停在第一个需要人类拍板的地方。自主模式改变的是「什么时候问人」,不是「什么时候可以不验证」:活路径验证标准、`PENDING_LIVE_VERIFY` 规则、产品码交 `feature-developer` subagent 的实现边界、loop 预算,全部原样适用。

## 第三段:最终验收(accept)

自主模式用「确认阶段的合同」换来了执行段的安静。本段是那笔交易的结账:**人类在这里第一次看到 AI 在无人监督期间替他做了什么。** 呈报的完整度就是这套模式的全部可信度——少报一条自决,自主模式就变成了「悄悄替你决定」。

0. **标记流程激活(flow marker),让机器 skill-gate 放行你在本流程内调用的步骤内技能。** 用 `write` 工具写单行 JSON 到 `<仓库根>/ai-nseos/state/flow/<session-slug>.json`(结构契约见 `FLOW_MARKER_CONTRACT.md`):`{"session_id":"<本会话 id>","started_at":"<ISO8601 UTC>","mode":"autopilot-accept","contract":"<一行合同要点>"}`。`session_id` 取本会话 id,勿猜、勿留占位符;`contract` 一行要点(单行、不含双引号);`<session-slug>` = session_id 的非法字符替换、拒绝 `..`。marker 一会话一文件,写仓库根;DSH 无 worktree,「主检出 / 共享 worktree」语义不适用。长流程跨小时要重写同一文件、`started_at` 重新生成。
1. **确认前置齐备,否则不开始验收。** 读本项目的 Profile 与 `ai-nseos/state/features/<feature-id>/` 全套,特别是第一段固化的四份文件:`RECON_REPORT.md`、`TEST_TARGETS.md`、`DELEGATION_MATRIX.md`、`DECISION_LOG.md`。四份缺任何一份,说明这个功能并没有真的走过自主模式的确认段——**停下来说明,不要凭现场推断补一份**,补出来的授权书是事后合理化,不是人类批准过的授权。这段说明同样按 `references/HUMAN_COMMUNICATION.md` 写,而它**发生在 Step 2 读那份 reference 之前**,所以真要停在这里,**先把它读了再开口**。写的时候别把内部文件名当解释丢过去(「缺 `DELEGATION_MATRIX.md`,无法验收」不是解释),要讲清他的处境:这个功能当初没有留下「哪些事可以由我替你决定」的书面约定,所以我现在没法告诉你我在你不在的时候做了哪些自己拿主意的决定——我能给你看做了什么,但给不出「哪些是你批准过的、哪些是我自己判断的」这条线。然后给推荐加理由:建议按协作模式那套来收尾(`nseos-review-feature` 逐项过),因为那条路不依赖事先的书面约定。可接受的入场状态是 `VERIFYING`、`PENDING_LIVE_VERIFY`、`READY_FOR_INTEGRATION` 或 `BLOCKED`(阻塞也要验收,人类需要知道停在哪);`IN_PROGRESS` 说明实施还没收尾,先回第二段。
2. **读真源。** 读 preset 内 `references/AUTONOMY_POLICY.md`——自主策略真源,本段要用到它的第二节红线、第三节拿到预授权级别后执行期怎么用(含执行期处置规则表)、第四节挂起语义、第五节分级打断阈值(可计算判据,含重算时机)、第六节测试修改两分法、第七节不放宽清单、第八节回滚粒度;再读 `references/HUMAN_COMMUNICATION.md`——**本技能里每一处向人类说话的地方,一律按它的七条规则书写,没有例外**。这是全覆盖的要求,不是一张清单:Step 1 的「四份文件不齐、停下来解释」、Step 5–8 的四项呈报、Step 9 里「不能单独回滚时让人类选替代方案」、Step 12 把门禁 deny 转述成人话,都在内,任何本文没预见到的临时说明也在内。**不要把它读成「只有『整份呈报』才适用」**——限定式的作用域正是漏掉对人环节的典型原因,呈报前后那两次才是最容易漏的。书写要点在 Step 4 展开。**预授权级别本身的判定与读法,唯一真源是 `references/AUTHORITY.md` 决策矩阵的第 4 列「可否预授权(autopilot)」**,查那里,本文不复述。另读 `references/STATE_MODEL.md`(挂起项与 `BLOCKED` 的区别、自主模式四份文件的位置)、`references/QUALITY_AND_EVALUATION.md`;发布门的机器判据见 `references/AUTONOMY_POLICY.md` 的发布门一节与 `references/AUTHORITY.md` 红线节;发布凭据(`.release-ready.json`)的格式与 head_sha 绑定唯一真源见 `references/RELEASE.md`。
3. **独立评审先于人类验收,本技能不替代 `nseos-review-feature`。** 自主模式里「实现的人」和「验收的人」都是 AI,自证的风险比协作模式更高,所以独立评审这一环不但不能省,还更要坐实:确认 `REVIEW_REPORT.md` 出自真正独立的 `quality-reviewer` subagent(涉及认证、数据、依赖或信任边界变化时加 `security-reviewer`)。若尚未做,先跑 `nseos-review-feature` 再回来。评审还要额外查两件本模式特有的事:(a) 产品码是否确由 `feature-developer` subagent 实现——无人监督下编排会话越界直改产品码的概率更高,`ai-nseos/state/.impl-boundary-ack` 里的越界记录要如实呈上(FB-20260716-006);(b) 状态文档之间是否自洽——`FEATURE_STATE.md` 抬头状态、其检查清单、`REVIEW_REPORT.md` 三者不得互相打架,且状态更新要已提交而非躺在工作树里(FB-20260719-005)。
4. **书写要点(适用于 Step 2 划定的全部对人环节,不只是这四项呈报),默认读者完全不懂 IT 技术。** `references/HUMAN_COMMUNICATION.md` 的七条规则在这里逐条落到实处:先用日常语言讲清背景再抛结论;每个决策与遗留项用**后果**表述而不是做法表述(不写「改用了乐观锁」,写「两个人同时改同一条记录时,后保存的人会看到提示、需要重新确认一遍,而不是悄悄把对方的修改覆盖掉」);术语首次出现即翻译,括号里可保留英文原文方便转发给技术人员,但括号不能替代解释;不许把技术权衡原样抛给读者让他自己提炼,先替他翻成钱、时间、用户体验、数据安全、以后好不好改;**严重性不可软化**——「可能丢数据」不许写成「有点风险」,「这个改动之后没法回退」不许写成「建议谨慎」,说人话失败的方向是啰嗦,不是含糊;每个需要裁决的项给推荐 + 一句同样说人话的理由。同时沿用给不在场读者写字的老规矩(FB-20260717-003):一条一行完整句子,内部编号与标签首次出现即解释,不许分号串联成段。**再叠加规则七(分层与篇幅,`FB-20260802-001`)**:开头 5 行内给「一句结论 + 需要你做什么 + 最多 3 条一行要点」,背景与证据放它下面;正文超过一屏(约 25 行)时结尾追加 3–6 条一行的「精炼版」(结论 + 待决策 + 风险);一条发现压到 1–2 行而不是一段。**砍的是修辞和过程,不是信息**——严重性、不可逆性、影响范围、数字与待决策项一个都不许因为求简而消失,与「精确性不可牺牲」冲突时后者赢,压不下去就分层。自主模式的验收呈报天然最长(执行期攒了一堆决策与挂起项),**它是最需要结尾精炼版的那一份**,也是最容易变成一堵墙的那一份。**在本段软化严重性是可记 finding 的缺陷**,因为读者会批准一件他并不理解其后果的事——那比看不懂更危险,它看起来像是被理解了。
5. **呈报一:测试目标清单红转绿对照表。** 填 `TEST_TARGETS.md` 的「验收对照」表并逐条呈报「`T-xx` 对应的 AC 编号 → 断言的业务语义(用人话那一列) → 确认阶段状态(红) → 现在状态 → 真实运行输出出处」。四条判据:
    - 没有真实运行输出的条目**不算绿**,写「未验证」;「部分通过」「跳过」「本地绿 CI 未跑」一律记红。
    - **执行期本就不允许给这张表新增行**(新增 = 扩验收标准)。因此若真出现了确认阶段没有的 `T-` 行,那是一次违规而不是一项成果:单列成一节,说明它是怎么被加进来的,并按「改已批准验收标准」交人类裁决,不要混在正常的红转绿里报上去。
    - 断言的**业务语义**若被改动过,同样单列高亮——那等于改验收标准,是人类的权力不是 AI 的。实现细节(mock 怎么搭、选择器、测试拆合、fixture、断言写法)可自主改,不必逐条呈报,但要能在决策日志里追溯到。
    - 附上统计表的最终数字(条目总数 / 已变绿 / 剩余未完成 / 其中被挂起阻塞 / 剩余可推进 / 比值),让人类一眼看到完成度而不是只看到一串绿勾。
6. **呈报二:活路径证据。** 用户可见的每条验收标准都要附真实运行的应用证据:真实 UI 截图、控制台与网络输出、真实 HTTP 响应、真实 DB 回读或 CLI 输出。**自主模式不降低任何证据标准**——绿测试加读代码永远不能把一条用户可见的标准判为通过,在 mock/stub 栈上的验证在需求本身针对真实路径时也不算数。缺证据或证据被推迟(推到迁移期、推到后续会话、推给用户)的,作为具名 PENDING 项写进 `FEATURE_STATE.md` 与 `HANDOFF.md` 并把功能置 `PENDING_LIVE_VERIFY`;在叙述里顺口提一句不解除这道门禁。**这里要专门查一遍:有没有哪条缺活路径证据的条目被记成了挂起项。** 挂起项享有「不阻塞主干、跳过去做别的」的待遇,缺证据不享有——把「没验」写成「被挂起」,等于用一个流程概念把一条没兑现的证据义务藏起来。查到就改回 `PENDING_LIVE_VERIFY` 具名行,并在呈报里点名这次记错。
7. **呈报三:决策日志逐条。** 把 `DECISION_LOG.md` 表一整张摊开,一条一行:`D-xx` 当时撞到了什么(触发情形,不是「做了什么」)、依据授权书的哪一条 `A-xx`、实际选择、影响了哪些文件、对应 commit、**能否单独回滚以及回滚动作是什么**。四件事要主动点名:标「类推自决」的要说明参照了哪条同类条目、为什么取了最保守的取向;**同一功能内类推自决超过 3 次必须显式指出**——那说明确认阶段的勘探漏得太多,是对下一次的诚实反馈;若某条决策与其它改动混在同一个提交里、无法单独回滚,**如实写明「不可单独回滚」并给出替代方案**(revert 整个提交、或另写一个反向改动),不要含糊过去;若授权书签署时人类勾的是「类推自决:不允许」,却出现了类推自决条目,那是越权,单独列出来。人类正是靠这张表行使否决权。
8. **呈报四:挂起清单。** 摊开 `DECISION_LOG.md` 表二,一条一行:`P-xx` 撞到了什么、为什么它不可预授权、影响了哪几条 `T-xx`、当前是否阻塞主干、有没有被解除。「为什么」那一栏应指向三种来源之一:`references/AUTHORITY.md` 决策矩阵第 4 列判为「否」的那一类;判为「有限可」但**越出了标注方向**(如接口改动越过「不破坏兼容」、新依赖落在白名单之外);或「撞到机器门禁 X」。第二种最容易被漏记成普通自决,验收时要专门看一眼有没有「有限可」条目实际上越了界还照常记进决策日志。另外把模板里的「门禁挂起记录」表一并呈上:**撞到机器门禁的挂起要显眼地单列**,如实写「差哪几项 + 已完成什么」——那是合法挂起,不是失败,更不是需要遮掩的东西。同时按 `AUTONOMY_POLICY.md` 第五节的算法说明当时为什么没有打断人类:剩余可推进条目(分母里剔除被挂起项点名的那些)占剩余未完成条目的比例是多少,是否跌破 30%,以及这个比值在「新增挂起 / 条目变绿 / 挂起解除」三种事件后都重算过。这一栏是在向人类证明「AI 看起来还在忙、实际只干边角料」没有发生。
9. **人类逐条裁决;否决的走回滚路径。** 呈报交付后等人类填 `DECISION_LOG.md` 的「验收结论」两张表:每条 `D-xx` 认可还是否决、每条 `P-xx` 是本轮补做 / 进 Backlog / 确认不做。被否决的条目按 Step 7 记录的回滚动作执行:能单独回滚的直接 revert 那个 commit,并在决策日志**追加**一行「已按人类裁决回滚」(表只追加、不改写、不删行),写清是谁、什么时候、为什么;不能单独回滚的,把替代方案连同代价一起说清再由人类选——**这是一次发生在呈报交付之后的选择请求,同样按 `references/HUMAN_COMMUNICATION.md` 写**:先说清他现在面对的是什么(你想撤掉的这一处,当初和另外几处改动一起提交了,所以撤不了单独一处),再把每个选项用后果表述(整块退回 = 那几处一起没了,包括你刚才认可的;另写一个反向改动 = 那处行为回到你要的样子,但代码里会多留一层补丁,以后改这块要多花时间),代价不许软化,最后给推荐和一句说人话的理由。**回滚要落在提交上,不是口头承认**——否则下一段集成时那份改动还在。
10. **回滚之后不是走捷径回到验收。** 任何否决导致的改动都让功能回到 `IN_PROGRESS`(或缺陷性质的回到 `NEEDS_FIX`),产品码的修改仍由 `feature-developer` subagent 按 TDD 实现,不由编排会话顺手补;修完重新跑 Step 5–8 里受影响的部分并重新呈报。**「都到验收了就别折腾」是本段最容易犯的错**,它会把人类的否决权变成走过场。
11. **推进状态。** 全部四项通过且人类接受了决策日志 → `READY_FOR_INTEGRATION`;实现看着成立但缺活路径证据或证据被推迟 → `PENDING_LIVE_VERIFY`,并把每项推迟记为 `FEATURE_STATE.md` 与 `HANDOFF.md` 里的具名 PENDING 项(只有这些具名项全部关闭后才能转 `READY_FOR_INTEGRATION`);按 `AUTONOMY_POLICY.md` 第五节重算后比值 < 30%、主干推不动 → `BLOCKED`,如实报清卡在哪、需要人类给什么。**自主模式不新增状态**——挂起始终是条目级概念,功能整体只在跌破阈值时才用既有的 `BLOCKED`。状态变更一律追加进 `FEATURE_STATE.md` 的历史,不覆盖既有记录。
12. **发布门 `action-gate` 的判据一字不放宽,本技能不代替它。** 那道机器门就是最终验收的执行点:`ai-nseos/state/.release-ready.json` 的 `review`(有真实独立评审报告,FB-20260716-003)、`prod_schema`、`doc`(本次改动引入或改动的域名词与业务规则是否已记进 `docs/domain/`,FB-20260720-002/-004)三个字段,该怎么判还怎么判。**三个字段永远不可预授权、不可自签充数**;门禁阀门(机器层门禁的逃生舱)属人类运维,模型不得自行关闭,也不得为跳过没做完的工作而请求关闭(逃生舱见 `DECISIONS.md` D5#10,人类运维、模型不得自关)。人类看到门禁 deny 时,由你按 `references/HUMAN_COMMUNICATION.md` 转述成人话,而不是把 deny 原文丢给他——那些文本的首要读者是模型。这条写死在这里,是因为「不打扰用户」的压力会把模型推向「自己想办法通过」:实测过一个长跑会话在反复回压下两次正确拒绝后,第三次执行了带阀门前缀的推送(FB-20260725-003)。

**验收通过不等于合并或发布授权。** 合并到保护分支、数据迁移、发布与回滚,依旧需要人类在本轮的单独明确授权;本段的产出是「可以去申请那道授权了」,不是那道授权本身。
