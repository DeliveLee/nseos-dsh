# 规划一个功能

0. 标记 ai-nseos 流程为激活,让机器 skill-gate 放行你在本流程内要调用的步骤内技能(头脑风暴、系统化调试、任何项目专用技能)。用 `write` 工具写单行 JSON 到 `<仓库根>/ai-nseos/state/flow/<session-slug>.json`:

```json
{"session_id":"<本会话 id>","started_at":"<ISO8601 UTC>","mode":"plan-feature","contract":"<一行合同要点>"}
```

- `session_id` 取本会话 id,勿猜、勿留占位:门禁据此归属 marker。`contract` 一行要点、单行、不含双引号。
- `<session-slug>` = session_id 的非法字符替换、拒绝 `..`。
- 长流程跨小时要刷新:重写同一文件、`started_at` 重新生成。
- 完整校验语义见 `FLOW_MARKER_CONTRACT.md`(空文件/错 session/过期 >4h → 门禁 deny)。

1. 若 `ai-nseos/PROJECT_PROFILE.md` 缺失或未初始化,先初始化它(幂等、低风险),再继续——不要让用户手动去做。
2. 读 `references/FEATURE_LIFECYCLE.md`、`references/LOOP_AND_SCOPE_POLICY.md`、`references/AUTHORITY.md` 以及 `templates/`。
3. 先按 Loop and Scope Policy 分类变更等级(Small / Standard / Complex / Exceptional)。Small 变更可用轻量模式:在会话内陈述合同要点(结果、范围与非目标、验收判据、所需证据),并在 marker 里以 `"mode":"lightweight"` 记录——与第 0 步同一套 `write` 规则(同一个「本会话 id」,勿猜、勿留占位),然后跳过功能目录。轻量模式降低的是文书,不是证据标准:一个没有活路径证据的 Small 变更仍是 `PENDING_LIVE_VERIFY`,不是完成。它也不允许跳过文档维护(FB-20260720-003):在已采纳文档体系的仓库里,收尾前明确判断一次——这次变更是否引入或改动了某个领域术语、某条业务规则(阈值/上限/校验/计算),或某个值得记录的模块/架构事实?没有就一句话说明;有就现在更新归属文档(`GLOSSARY` / `BUSINESS-RULES` / 架构文档)或记入 `OPEN-QUESTIONS`,而不是留给每周 doc-audit 巡检事后去追。这跟机器 action-gate 在发布时通过 `ai-nseos/state/.release-ready.json` 的 `doc` 字段追的(FB-20260720-004)是同一项义务——旧版 FB-003 的措辞只存在于 `nseos-plan-feature` 里,而轻量工作往往直接写 flow marker 就绕过本技能,所以发布时那次 ack 才是轻量路径上真正会触发的兜底。在这里就把维护做了(并记录),发布时 ack 就只是一行确认,而不是临场补课。实质性功能——跨模块、公共接口、数据模型、迁移、对外发布或高风险——一律要求完整的功能目录。
4. 完整模式:分配/确认一个项目内唯一的功能 ID,并按 `templates/FEATURE_CONTRACT.md`、`templates/IMPLEMENTATION_PLAN.md`、`templates/FEATURE_STATE.md`、`templates/REVIEW_REPORT.md`、`templates/HANDOFF.md`、`templates/BACKLOG.md` 创建 `ai-nseos/state/features/<feature-id>/`。
5. 不要改业务代码。
6. 对欠定义或新功能,需求发现是本流程内的第一步——头脑风暴/意图澄清属于这里,不是一条绕过合同的独立顶层流程。用户可见或欠定义的行为,用 `subagent` 工具派 `product-analyst` 角色的子代理;跨模块、接口、数据、依赖或运维影响,派 `architect` 角色的子代理。对 `Complex`/`Exceptional` 等级这不是可省的表面功夫(FB-20260719-004):要么真的派至少一个分析子代理并保留其输出,要么在合同里记录为什么跳过、由谁负责那个视角。嘴上说「我会派 product-analyst/architect」然后在编排会话里自己把发现做了,不算完成这一步——一个复杂的跨模块变更值得第二双独立的设计眼睛。**发现阶段你向人类提的每一个澄清问题都按 `references/HUMAN_COMMUNICATION.md` 写——默认读者完全不懂 IT**(这与第 10 步描述的 FB-20260717-003 是叠加关系;两者解决不同的问题)。这是交互模式下人类提问量最大的界面,也是术语伤害最大的地方:发现阶段你问的是「产品应该做什么」,所以一个用实体、端点、状态机措辞的问题要么被跳过、要么得到一个猜的答案,然后你带着这个答案做完整条功能。问业务处境、问用户身上应该发生什么;把问题批量提出,不要一条条往外挤。
7. 对照本仓库调校发现。绝不复用别的项目的假设。
8. 记录目标、非目标、Required/Expected/Optional/Out-of-scope 分类、允许/禁止路径、依赖、风险、验收判据、证据、循环预算与审批。
9. 写一份小的可逆实施计划,并更新项目功能索引(`ai-nseos/state/FEATURE_INDEX.md`;它的归属者、更新点与诚实边界在 `references/STATE_MODEL.md`——你在这里建的那一行必须在之后每次状态迁移时重新对齐,因为一份最后一次写在规划时刻的账本,会显示成「等待审批、没有分支」,而功能其实几小时前就上线了)。
9.5 **若计划跨多个阶段、批次或会话,还要产出一份机器可判的进度 manifest(`FB-20260727-001`)。** 用 `templates/PROGRESS_MANIFEST.md`:每个可判条目一行,配一句「什么样算完成」、一条可运行的检查命令、一个 `machine`/`human`/`hybrid` 等级,外加一个记录生成 HEAD 的头与一条「manifest 一旦过期就以非零码退出」的陈旧检查命令。只有范围散文扛不住这个:在一个真实的 8 阶段计划里,每个恢复锚点都可读且正确,但一条会话内的指令(「把剩下 6 条做完」)把整个执行会话锚定在本地清单上,产出了 47 个 commit,并回答「六条全做完、没有遗留」——而那六条大约只是阶段 1 的六分之一,阶段 2..7 还没开始。**散文从不失败;命令才会。** 对着这样的计划报告完成时,永远报三个数——本阶段、整个计划、剩余阶段按名字列出。三条判据,不是一条(`FB-20260803-002` / `-003`):陈旧必须让命令失败;**无效或静默退化的输入也必须让命令失败**(指纹能抓住「旧」,抓不住「错」,而「新但错」看起来和「新且对」一模一样);而且这些失败必须挂在仓库自己认定的权威门禁上——一条只有等有人记得去敲才会失败的命令,对下一个会话等于不存在。**诚实边界:没有机器门禁检查这份 manifest 是否存在、`enforced_by` 里写的那道门禁是否真实、或它是否真的会跑那些命令**——与 `references/STATE_MODEL.md` 里功能索引的边界相同。只说「必须产出」而不说「没有任何东西会抓它的缺失」,读者就会以为有一张安全网。
10. 状态置为 `AWAITING_APPROVAL`,只呈报实质性的产品、架构、安全与成本决策。写给一个没看过过程的人(FB-20260717-003):开头用大白话给结论和「必须决定什么」;每个决策单独一行,带推荐选项和一行理由;每个内部 ID、锚点、标签首次出现即解释——绝不写一句分号串联的密段落。**在这之上,默认读者完全不懂 IT——按 `references/HUMAN_COMMUNICATION.md` 措辞。** 这两条是叠加,不是重叠:FB-20260717-003 解决「读者没看过过程」,`HUMAN_COMMUNICATION.md` 解决「读者不懂技术」(每个选项陈述成用户或业务会经历的后果,而不是你打算写的实现;每个技术词首次出现即翻译;绝不为了通俗而软化一个不可逆或丢数据的后果)。这道门是要从人类那里拿到一个*业务*决策;一份用工程语言写的批准请求会被橡皮图章盖过,那和没问一样地让门失败。**再叠加规则七(分层与篇幅,`FB-20260802-001`)**:开头 5 行内给「一句结论 + 需要你做什么 + 最多 3 条一行要点」,背景与证据放它下面;正文超过一屏(约 25 行)时结尾追加 3–6 条一行的「精炼版」(结论 + 待决策 + 风险);一条发现压到 1–2 行而不是一段。**砍的是修辞和过程,不是信息**——严重性、不可逆性、影响范围、数字与待决策项一个都不许因为求简而消失,与「精确性不可牺牲」冲突时后者赢,压不下去就分层。一份没人读完的批准请求和一份看不懂的批准请求,对这道门的破坏是一样的。

停。只有记录在案的人类批准把状态改成 `APPROVED` 之后,实现才开始。
