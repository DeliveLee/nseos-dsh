# 文档审计(doc-audit)

在一个业务仓库里,随着代码演进和域文档积累,文档会悄悄失真、也会攒出噪声。本 skill 有**两种模式**:

- **漂移模式(drift,默认)**——回答「代码改了 → 哪条文档过期了」。变更触发,适合高频(每日 / 每次 PR 前)。走下面 Step 1–8。
- **整体体检模式(holistic / 体检)**——回答「攒了这么多域文档,整体还健康吗」。不依赖代码改动,通读全部文档找**跨域矛盾 / 重复 / 孤儿 / 陈旧 / 剪枝候选 / 结构问题**。适合低频(月度或域数量明显增长时)。走下面「整体体检模式」节。
- 调用:`$ARGUMENTS` 含「体检 / holistic / full」→ 走体检模式;否则默认漂移模式。

它改编自一份线上 drift-audit skill,但**适配 nseos 的知识分层**:`AGENTS.md`(薄索引)/ `docs/domain/*`(业务语言与规则)/ `docs/architecture{,/<module>}.md`(模块地图)/ `.claude/rules/*`(路径绑定规矩)/ `.claude/skills/*`(开发 SOP)/ `ai-nseos/PROJECT_PROFILE.md`(治理详情)。

先读 `references/KNOWLEDGE.md`,那里是这套分层的治理原则;本 skill 只是它的手动执行流程。两种模式都遵守文末「约束(硬)」。

## Step 1 — 切到集成分支

切到该 repo 的**集成分支**(PR 的 target 分支),以 `AGENTS.md` / `ai-nseos/PROJECT_PROFILE.md` 里记录的约定为准:团队模型通常是 `staging`;**单干模型的仓库可在 PROJECT_PROFILE/AGENTS 里声明 `Doc-audit PR target: main`,声明后 main 即合法集成目标**。两者都没有就**问,别默认 `main`**——很多团队 `main` 是发布分支、`staging` 才是集成目标,审错分支会漏掉或误报漂移。这一问同样按 `references/HUMAN_COMMUNICATION.md` 写(下面 Step 5.5 有该规则与 `FB-20260717-003` 叠加关系的完整说明):别问「集成分支是 `main` 还是 `staging`」,要问「我改好的文档先提到哪个分支等人看?是团队日常合并新功能的那个,不是直接对外发布的那个」。

## Step 2 — 审视近期改动的 diff

```bash
git log --since="<上次审计日期或约定窗口>" --stat -- '<按仓库语言调整的 globs>'
```

按仓库语言调整 globs(如 `'*.ts' '*.tsx'` / `'*.py'` / `'*.go'` / `'*.java'`)。逐个 commit 看 diff。当 commit message 引用了 issue / PR 编号时,用 `gh pr view <n>` 拉出上下文,理解改动意图,而不是只看代码表面。

## Step 3 — 判断每处改动是否让某条文档主张失效

对每处改动,问「有没有哪条文档因此变得不准确」。重点信号:

- 重命名 / 删除了实体(表、字段、函数、类型、API、工具);
- 业务词与代码实体错配(文档用的业务说法已经不对应现在的代码实体);
- 状态机、状态流转、阈值、金额、计算规则变化;
- 模块新增、拆分、合并,或模块责任 / 入口 / 数据流改变;
- 接口 / API 的形状或返回信封(envelope)变化;
- 命令变化(build / test / lint / run / DB 迁移等);
- 新增、移动或重命名了文档或模块文件。

## Step 4 — 路由到「拥有它的那一层」(单一真源,一处修不重复)

每条失配只在**一个** owner 层修正,不跨文件重复写:

- 业务词 / 命名 → `docs/domain/GLOSSARY.md`
- 业务规则 / 数字 / 阈值 → `docs/domain/BUSINESS-RULES.md`(**连算例里的数字一起改**,别只改规则留下过期算例)
- 跨域词义、同词多义、新增域 → `docs/domain/CONTEXT-MAP.md`
- 状态机 / 业务流程 → `docs/domain/WORKFLOWS.md`
- 模块新增 / 改责 / 入口 / 数据流 → `docs/architecture.md` 及对应 `docs/architecture/<module>.md`
- 某模块特有的坑 / 约束 → 该模块的 architecture 子文件或对应 `.claude/rules/*`
- 路径绑定约定 → 匹配的 `.claude/rules/*`(代码移了位置,**同时改 `paths:` glob**,让规则继续命中)
- 开发 SOP 步骤 → 对应 `.claude/skills/*`
- 仅当是跨全项目的硬规矩 → `AGENTS.md` 的 Hard Rules 或 Always / Ask First / Never
- 命令 → `AGENTS.md` 的命令段

## Step 5 — 保层不变量(硬)

修正时不得破坏分层结构:

- `AGENTS.md` 保持**薄索引**(< 150 行):细节下沉到 docs/ 与 rules/,这里只留指针。别把规则正文搬进来。
- `docs/architecture.md` 保持**索引**:单个模块的细节进 `docs/architecture/<module>.md` 子文件。
- `GLOSSARY` 保持「按 bounded context 分块 + 5 列表格 + 行为铁律」的结构,别把它改成大段散文。
- `.claude/skills/*` **只引用知识、不复制知识**。若某 skill 抄了一份现在已变的规则,改的是 docs/ 里的真源,然后让 skill 指过去,而不是就地改 skill 里的副本。
- 文档 / 模块文件的增删移动,要同步更新 `AGENTS.md` 里的文档地图与 `docs/architecture.md` 里的模块地图,并**验证所有链接可达**。

## Step 5.5 — 矛盾检测

除了「代码 vs 文档」,还要显式挑出「文档与文档之间」「同一事实在多处不一致」的冲突。把这些矛盾列成清单**交给人裁决**,不要 skill 自行选一个版本改——你可能把对的改成错的。

**裁决清单按 `references/HUMAN_COMMUNICATION.md` 书写——默认读者完全不懂 IT 技术。** 它与既有可读性要求(`FB-20260717-003`:结论先行、一条一行完整句、内部编号首次出现即解释)是**叠加**关系,不是替代:前者解决「读者没跟看过程」,后者解决「读者不懂技术」(选项按后果而非做法表述、术语必须翻译、严重性不得软化)。每条矛盾要说清「按甲说法业务上意味着什么、按乙说法又意味着什么」,而不是并排贴两段文档原文。本规则适用于本 skill **每一处**面向人类的提问与呈报——包括但不限于 Step 5.8 的质量闸标注、Step 8 的 PR body、体检模式产出的健康报告与剪枝候选确认、以及「无声明又无其它集成分支 → 跳过并报告」那类跳过说明(上面这串是举例不是穷举,别把没列到的当成不适用)——**剪枝确认尤其要说清「删掉这份文档以后谁会因此不知道什么」**,读者不该为了判断能不能删而先去读那份文档。

## Step 5.8 — 质量闸(标记 → 可选软拦)

对被触及的文档做一次质量判断(借鉴 awesome-claude-md 评分思路):内容深度 / 教育价值 / AI 可用性约占 70%,成熟度 / 社区约占 30%。低于阈值的段落标注「待补」(PENDING)交人处理,**不要直接删**——薄弱的文档也可能是唯一记录。

**软拦(opt-in)**:默认只「标记」;若仓库开启软拦(`AGENTS.md` / `PROJECT_PROFILE.md` 里注明,或 PR 约定),则把低于阈值的项在 **PR body 顶部醒目列为「合并前必须处理或显式接受」**,并在 PR 里打 `needs-review` 之类标签——**不是硬拦合并**(doc-audit 本就只开 PR、由人合),而是让低质内容无法被无声合入。绝不因低分自动删除或阻断。

## Step 6 — 只做精准修正

只改真正失配的地方。不重写仍然准确的段落,保留原有语气与结构。目标是让文档重新对齐代码,不是重写文档。

## Step 7 — 无漂移

若本轮没有发现任何失配,不开 PR,记录一行:`No drift detected.`

## Step 8 — 有漂移则开 PR

从集成分支切一个 feature 分支,**只提交 `*.md` 文档改动**,开 PR:

- 标题:`docs: 文档审计 — <YYYY-MM-DD>`
- body 逐条列出:每处修正 / 它落在哪一层(owner 文件)/ 触发它的 commit SHA。
- **标注"本可在开发中维护"的漂移(FB-20260720-003)**:对每处漂移,若它源自一个 feature 的开发改动(该 feature 本应在 build/plan 时就维护对应文档),在 body 里标一下,并给出这类条目的计数。目的是让「本该开发中随手维护、却漂到一周后由无上下文的 sweep 补」的退化**可见**,而不是被 sweep 静默吸收——sweep 是安全网,不是文档维护的主力。

## 整体体检模式(holistic / 体检)

漂移模式回答「代码改了→哪条文档过期」;体检模式回答「攒了这么多域文档,整体还健康吗」。**不依赖代码改动,通读全部** `docs/domain/*`、`docs/architecture{,/<module>}.md`、`AGENTS.md` 文档地图,逐项排查(切集成分支同 Step 1):

- **H1 跨文档矛盾**:同一事实(术语定义、状态机、规则数字)在两处说法不一;跨 bounded context 的同名词被错误当成同一实体。列清单**交人裁决**,不自行选版本。
- **H2 重复 / 单一真源违规**:同一条事实在多处**正文重复**(不是"指针"而是复制)。保留 owner 层那一份,其余改成指针。
- **H3 孤儿文档**:存在于 `docs/` 但**没有任何文档地图 / 索引指向它**(AGENTS.md 文档地图、architecture 模块地图都没有)——AI 永远不会加载它,等于噪声。要么补指针纳入,要么标剪枝候选。
- **H4 陈旧 / 被取代**:抽样核代码,引用的 `file:line` / 实体 / 命令已不存在;或 `OPEN-QUESTIONS.md` 里已解决却没归档、已归档却还占着待确认表;或长期未动而所述模块已重构。
- **H5 剪枝候选**:低信号(写的都是 AI 能从代码直接读出的东西,违反「只写猜不到的」)、被更权威文档取代、或已无对应代码的历史件。**列为候选交人确认,绝不自动删**。
- **H6 结构健康**:AGENTS.md 是否仍 < 150 行;GLOSSARY 是否仍按 bounded context 分块;是否有 context 缺 CONTEXT-MAP 对照;所有文档地图链接是否可达。
- **质量评分**:对每份 domain 文档按 Step 5.8 打分,低分列「待补/待剪」(软拦仓库进 PR 醒目区)。

产出一份**领域文档健康报告**(矛盾 / 重复 / 孤儿 / 陈旧 / 剪枝候选 / 结构 / 低质,各带定位),按 Step 8 开 PR:可安全修的直接修(路由到 owner 层),需人裁决 / 剪枝的列 PR body。**同样只改 `*.md`、只开 PR、不自动合、剪枝一律走人确认。** 无问题则记 `No issues found (holistic).`

## 手动 sweep 与路由提醒(DSH 无定时调度——诚实缺口)

**DSH 没有定时调度(无 cron),本 skill 无法自动每周巡检。这是一个显式降级,不是对等实现。** 漂移检测只能由两件事触发:

- **路由提醒**:路由层检测到某仓文档可能 stale 时,在会话里加一行提醒,让你手动跑本 skill(漂移模式)。
- **手动 sweep**:用户或维护者说「跑一次 doc-audit」,对当前业务仓库跑本 skill(默认漂移模式;说「doc-audit 体检」跑体检模式)。体检应低频手动执行(月度,或域文档数量明显增长时)。

新仓库一旦被初始化 + 生成 GLOSSARY,同样适用本 skill;单个仓库若要跳过,在它的 `ai-nseos/PROJECT_PROFILE.md` 注明,手动 sweep 时尊重它;nseos preset 源仓库自身豁免(同 route-work 的源仓库豁免)。**自动巡检的缺失意味着:没有主动提醒或手动触发时,文档漂移不会被发现——不要把「有提醒」当成「有自动巡检」的安全边界。**

## 约束(硬)

- **只改 `*.md`,绝不碰代码。**
- **只开 PR,绝不自动合并,绝不直接 commit/push 到主干**(`main` / `master`)。PR 的 target 遵循 Step 1 解析出的集成分支;**当且仅当**该仓 `ai-nseos/PROJECT_PROFILE.md` 或 `AGENTS.md` 含显式声明行 `Doc-audit PR target: main`(单干模型:main 即集成分支)时,PR 才允许 target `main`/`master`——PR 本身就是人类合并门禁,这条防的是无声改主干,不是防「经人审的 PR 进 main」。无声明又无其它集成分支 → 跳过并报告,不猜。
- 若已有一个开着的 PR 覆盖了同一处改动,**不重复开**。
- **不要因为 `.claude/` 被 gitignore、云端 checkout 看不到就删掉对 `.claude/rules/*` 或 `.claude/skills/*` 的引用**——它们很可能是本地真实存在的文件。保留引用,并在 PR body 里标注「待人确认」。
