# 生成领域知识(GLOSSARY / BUSINESS-RULES)

本技能把「藏在人脑与代码里的 tacit 业务知识」转成「人与 AI 都能直接引用的知识层」,产物统一落 `docs/domain/`(至少 `GLOSSARY.md`、`BUSINESS-RULES.md`、`OPEN-QUESTIONS.md`)。

**红线:本流程只产草稿。任何草稿在经过「人 + 业务方 review」并标记可信度之前,绝不当作定稿,绝不被 plan/build/review 当权威引用。** AI 能从代码里读出「是什么」,但读不出「为什么、该不该、业务真意」——那一半必须由人补。

## Step 0 前置

- 确认目标仓库已初始化(存在 `ai-nseos/PROJECT_PROFILE.md`);未初始化先初始化。
- 读 `AGENTS.md`、现有 `docs/domain/*`、以及 preset 内 `references/KNOWLEDGE.md`,对齐已有术语与本仓库的知识工程约定,避免重复造词。

## Step 1 读代码产草稿(AI 的一半)

派**只读** subagent(用 DSH `subagent` 工具,仅 Read / Grep / Glob)扫描本次目标业务线的实体、字段、状态机、枚举与命名,产出两份草稿:

1. **GLOSSARY 草稿** —— **按 bounded context 分块**(每个上下文一节,不跨界拉平)。每节用 5 列表:`术语 | 标准定义 | 对应实体/表/字段 | 别名/误用 | 可信度`;关键实体额外用散文写清它的**行为铁律**(什么情况下允许/禁止、状态如何流转)。
2. **`OPEN-QUESTIONS.md`** —— 代码回答不了、必须业务确认的开放问题清单,每条带 `文件:行号` 佐证「为什么会问到这」。

约束:引用代码一律用 `文件:行号`,**不粘代码块**;凡只能从代码推断、无法确证业务意图的,显式标 `(inferred)`。

## Step 2 人 / 业务方补充(人的一半)

把 `OPEN-QUESTIONS.md` 交给懂业务的同事。**这一步的读者按定义就是「懂业务、不懂代码」的人,提问一律按 `references/HUMAN_COMMUNICATION.md` 书写**——它与既有可读性要求(`FB-20260717-003`:结论先行、一条一行完整句、内部编号首次出现即解释)是**叠加**关系而非替代:前者解决「读者没跟看过程」,后者解决「读者不懂技术」(选项按后果而非做法表述、技术术语必须翻译、严重性不得软化)。问「这张表的 `status` 字段枚举值分别代表什么」得不到答案;问「一张单子从下单到收款中间会经过哪几种情形、每种情形下客服能做什么」才能。引导技巧:

- 用 **chapter markers** 按业务域切分,一次只聊一个上下文,避免跳跃。
- **worked examples 用具体数字**(真实单号、真实金额、真实数量)去逼出隐藏假设与误解,而不是抽象提问。
- 把对方的口述用**结构化语言复述一遍**回读给他确认,靠冗余暴露理解偏差。

## Step 3 矛盾检测

显式把三方冲突挑出来交人裁决,**不擅自定论**:

- 代码事实 vs 业务口述;
- 业务口述 vs 现有文档;
- 现有文档 vs 代码事实。

每处冲突写清各方说法与出处,标 `CONFLICT`,等人给出裁决再落盘。裁决请求同样按 `references/HUMAN_COMMUNICATION.md` 写:先用日常语言说清「按 A 说法系统会怎样、按 B 说法会怎样」,再让人选,而不是把两段代码事实并排贴出来让他自己提炼差异。

## Step 4 人工纠错落盘

- 合并前三步结果,为每条知识标可信度:`validated`(人 + 业务已确认)/ `inferred-from-code`(仅代码推断)/ `unverified`(尚未证实)。
- 经**人 + 业务方 review** 后写入 `docs/domain/*`;已解决的问题从 `OPEN-QUESTIONS.md` 移除,未解决的保留并带最新状态。

## 词汇纪律

- **一个概念只保留一个标准词**;其余写进「别名/误用」列指向标准词。
- **bounded context 不拉平**:同一个词在不同上下文含义不同时,分上下文各自定义,不强行统一。
- **命名(表 / 字段 / API)也是词汇决策**:发现坏命名、名不副实、一词多义的命名,记进 `OPEN-QUESTIONS.md` 或改名 backlog,不在本流程里擅自改代码。

## 与其它组件的关系

- 与 `domain-knowledge` subagent 角色:本技能的产物(`docs/domain/*`)是该只读角色的取信来源,供 plan / build / review 阶段解词问答。知识层越干净、可信度标注越清楚,该角色的回答越可靠。
- 与 `nseos-doc-audit`:本技能负责**从无到有建 / 补**知识层;`nseos-doc-audit` 负责**保鲜**——代码演进后检测知识层与代码漂移。两者互补,不重叠。
