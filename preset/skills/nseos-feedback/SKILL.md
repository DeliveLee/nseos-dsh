# 记录 nseos preset 反馈(feedback)

观察:本会话里真实发生的流程摩擦(命令 / 报错原文 / 文件路径),由模型当场归纳(DSH 的 skill 工具不接收调用参数,观察对象从上下文取)。

**主动触发(FB-20260719-001)**:不要等人来问。特别是同一个会话里为了绕开**同一个**框架限制折腾两次以上——比如 action-gate 的标记中途过期、`标记 → 凭据 → push` 这串要反复重试、subagent 被会话/额度截断——那就是可归纳的反复摩擦:**当场**起草一条,不要留到以后。反复绕过而从不进入队列的摩擦,下一轮维护无从收敛,于是它原样复发。

## 为什么捕获和发送是两步(别改回一步)

旧版把条目直接追加进 preset 源仓库的 `feedback/INBOX.md`。这条逻辑只对维护者一个人成立——只有他的环境指向自己的工作仓库。对团队成员,那个路径是 preset 的安装副本(升级会被覆盖):写入看似成功、用户被告知「已记录」,而条目永远没有离开他的电脑。维护者因此无法区分「没人有意见」和「所有意见都丢了」。

所以现在:

- **捕获**落在本机队列文件,**必须永不失败**。它发生在人正烦躁的时刻——那是最不能要求联网、登录或做决定的时刻。
- **发送**是独立的、需要明确确认的一步。**没发出去就必须照直说「还没发出去」**——静默排队等于把原来那个 bug 换个地方重演。

## Step 0 — 先判断这是哪个产品的问题

这个反馈渠道只收**这个 nseos preset(DSH 版)**自己的问题。如果摩擦来自 nseos 的**移植版 / 适配版**(Codex 版 `ai-nseos-codex`,或任何其它宿主),条目属于**那个移植版自己的仓库**——那里才有它的源码、发版周期和回归测试。记到这里会变成一条谁都没法处理的条目。拿不准就问一句:这次是在哪个宿主里跑的。

## Step 1 — 分两条路:维护者 vs 使用者

- **当前目录就是 nseos preset 源仓库**(本仓库即 nseos preset 源仓库,含 `preset/` 技能目录,且可写)→ 你就在能改代码的地方,**直接追加到本仓库的 `feedback/INBOX.md`**,不必绕队列和 issue。格式见 Step 2 的条目模板。
- **其它任何情况**(团队成员、任何业务仓库、任何安装方式)→ 走本地队列。**绝不要**去写 preset 的安装副本:那会在下次升级时被覆盖,而且那些条目没人读得到。

## Step 2 — 捕获进本地队列(永不失败)

用 `write` 工具,**一条一个文件**,写到 `~/.dsh/ai-nseos-feedback/`(机器本地、离线可用;单个共享文件会被并发会话覆盖,所以一条一文件)。文件名:`<ISO8601 时间戳>-<slug>.md`。条目内容:

```markdown
- Title: <一句话标题>
- Severity: P2
- Component: <skill/agent/reference/模板路径,或 overall>
- Project: <仓库/项目名>
- Date: <ISO8601 UTC>
- Observation: <实际发生了什么,带具体证据——命令、原文引用、文件路径>
- Expected: <这个流程本该怎么做>
- Suggested change: <可选,具体到能改的那一处>
```

严重程度:`P0` 危险指引 / `P1` 被卡住或结果错 / `P2` 摩擦与多余负担 / `P3` 打磨与想法。**一个问题一条,不要把不相关的问题打包**。

记事实、不记指责:把失灵的那条规则原文引出来,连同它失灵的真实场景。**条目本身写给维护者,保留全部技术细节**——引用的规则原文、命令、文件路径,一个都不要软化。

## Step 3 — 问要不要现在发送(内容离开这台电脑之前必须过这一关)

**默认问一句,而不是默认发送。** 理由不是礼貌:条目按设计就带命令、报错原文和文件路径,那些来自**用户自己的业务仓库**,可能有客户代码、内部命名、日志里的凭据。这是一次对外发布,**不存在「默认同意」**。

1. **脱敏**:把家目录和绝对路径收敛成 `~`(路径的诊断价值保留,机器和人名去掉)。**命中疑似密钥/口令时,拒绝并指出行号**——这时**不要**替用户删掉那几行然后照发:告诉他第几行像什么,让他自己改或者决定不发。发布是不可逆的,一个 token 进了 issue,事后删掉 issue 也已经泄漏了。
2. **把脱敏后的原文摆给他看**,一字不改。然后问一句要不要发。
3. 拿到明确同意后,把脱敏后的正文写成一个临时文件,再:

   ```bash
   gh issue create -R DeliveLee/nseos-dsh -l feedback -l "<P0|P1|P2|P3>" \
     -t "<一句话标题>" -F <脱敏后的临时文件路径>
   ```

   成功(拿到 issue 链接)后标记已发:把该队列文件移入 `~/.dsh/ai-nseos-feedback/sent/`,它就不再计入未发数、也不再被每轮提醒。
4. **发送失败或用户说不发 → 条目留在队列,并明确告诉他「这条还没发出去,我这边收不到」。** 绝不能因为命令没报错就说成已提交。最常见的失败是没装 `gh` 或登录过期,补救是 `gh auth login`;这两种情况都**不要**反复重试,说清楚然后继续原来的工作。

## Step 4 — 发送整条队列 / 导出

- **发送队列**:先报出有几条、最早那条多久了,再逐条走 Step 3。**逐条确认还是一次性确认由用户定**,但脱敏后的原文必须让他看到(条目多时可以给摘要 + 逐条标题,并说明「你要看哪条的全文我就展开哪条」)。
- **导出**:给拿不到 `gh`、或内容敏感到不该进 issue 的情况。产出一个已脱敏的合并文件,把路径给用户让他自己发给维护者。**疑似含密钥的条目会被跳过并单独列出**——照实转告,别让他以为全都在里面了。

## 注意

- **不要在使用方的会话里改 preset 行为,只捕获。** 修复发生在源仓库,经 `nseos-maintain` 技能(它会同时读 INBOX 和 issue 列表)。
- **立刻继续被打断的工作**;记反馈不能把当前任务带偏。
- **本 skill 不写流程标记**——它不进入任何交付流程。
- 每轮路由会在「队列里有未发条目且(≥3 条 或 最早那条超过 24 小时)」时加一行提醒(机器注入,见门禁 `unsentFeedbackBlock`)。**「用户说不想发就别在同一会话反复提」是模型纪律,不是机器 latch**——门禁每回合都会注入提醒,是否再次张口问人类由模型判断,别把这条写成「机器会停止提醒」。

对用户说的每一句话按 `references/HUMAN_COMMUNICATION.md` 写——**默认读者完全不懂 IT**。这与既有可读性要求(FB-20260717-003:结论先行、一条一行完整句、内部编号首次出现即解释)是**叠加**关系:前者解决「读者不懂技术」,后者解决「读者没跟看过程」。用一句平实的话说清:**他刚才哪里不顺,以及修好之后会有什么不同**。**不要让他自己选 P0–P3**,描述后果并给出建议档位 + 一句理由。
