## 怎么写这份报告

**整份报告按 `references/HUMAN_COMMUNICATION.md` 书写，不只是某一列。** 它是强制交付节点——人类要读它、并在读完之后据此批准授权书，所以它的读者默认不懂技术。

两张表里的每一条都要让他能回答「**这对我意味着什么**」，而不是只有工程师看得懂的结论。术语首次出现即翻译，严重性不许软化（规则五）。

「未验证疑点」那张表尤其要下功夫：**它直接决定授权书里那些默认处置是否被真正理解地批准。一条他没看懂的疑点，等于一条他没真正批准的授权**——而执行期 AI 会拿着那条授权在无人在场时自决。写得让他看懂，是这份报告存在的理由，不是附加要求。

| # | 结论 | 证据类型 | 证据出处 | 对本功能的意味 |
|---|---|---|---|---|
| F-01 | | 命令输出 / HTTP 响应 / 测试结果 / DB 回读 / 代码位置 / UI 观察 | <命令、URL、`path:line`、截图路径> | |

## 未验证疑点

**这张表直接决定《授权书》的条目**——授权书里的每一行都必须能追溯到这里的一个编号。因此这张表宁可长，不可漏。

| # | 疑点 | 为什么没验 | 撞上了会怎样 | 建议的默认处置 | 可否预授权 |
|---|---|---|---|---|---|
| U-01 | | 成本过高 / 需要生产数据 / 需要人类决策 / 环境不可得 / 时间预算耗尽 | | | 可 / 有限可 / **否** |

- 「为什么没验」写具体原因，不写「时间不够」这类无信息词。
- 「撞上了会怎样」写后果，按 `HUMAN_COMMUNICATION.md` 规则五：不许软化严重性。
- 「可否预授权」按 `references/AUTHORITY.md` 决策矩阵第 4 列判定，那里是唯一真源；执行期拿到级别后怎么用，见 `references/AUTONOMY_POLICY.md` §3。判「否」的条目在执行期一律挂起，不进授权书的自决部分；拿不准落在哪一类时按「否」填。
