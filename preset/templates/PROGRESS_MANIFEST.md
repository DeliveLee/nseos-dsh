# Progress Manifest（可判进度清单）: <PLAN-ID> — <Title>

多阶段 / 多批次计划的**唯一进度真源**。`plan-feature` 在计划跨越多个阶段、多个批次或多个会话时必须产出这一份（`FB-20260727-001`）。

## 为什么是一张表而不是一段话

**散文不会失败。** 进度写在计划文档、看板、执行协议、交接单四处散文里时，每一处都可能停在不同的日期上，而没有任何一处会因为过期而报错——过期的看板与准确的看板长得一模一样。

实测后果：一个 8 阶段计划的执行会话，被一句对话内的局部指令（「先完成剩余 6 项」）锚定，连做 47 个提交，被问「所有任务都完成了吗」时回答「六项全部完成、没有未完成的任务」。那 6 项约等于阶段 1 的六分之一，阶段 2..7 一个字没动。**恢复锚当时全部可读且内容正确**——问题不在没有锚，在于锚是散文，散文不参与判断。

所以这张表的判据是三条，缺一条都会让它退回散文：

1. **「这份清单过期了」必须能让某一条命令失败。**
2. **「这份清单的输入不合法、或被静默降级了」也必须能让某一条命令失败**（`FB-20260803-002`）。指纹只解决「旧」，不解决「错」——而**新鲜的错数据和新鲜的对数据长得一模一样**，跟过期看板与准确看板长得一模一样是同一个病。
3. **这些失败必须是「被强制」的，不是「可得」的**（`FB-20260803-003`）：那条命令得挂在**本仓库自称权威的那道门**上（CI job / 合并门 / 发布前置门）。只要它还只是「一条你记得敲就会红的命令」，一个没读过这套约定的新会话就不会去敲，于是清单在它手里等于不存在。

## 头部（生成时写入，不手改）

```yaml
plan_id:        <计划标识>
generated_at:   <UTC 时间戳>
generated_head: <生成时的 git HEAD sha>
source:         <计划文档路径 —— 范围散文的真源，与本表互补>
staleness_cmd:  <一条命令：当 HEAD 已远离 generated_head 或某条判据失效时必须非零退出>
schema_cmd:     <一条命令：当生成这份清单的手工输入不合法时必须非零退出>
enforced_by:    <上面两条命令挂在哪道门上：门的名字 + 它的定义在哪个文件的哪一行>
```

`generated_head` 是这份清单的保质期锚点。**HEAD 前进而清单没重生成 = 清单可疑**，`staleness_cmd` 要能把这件事变成一次失败，而不是一句提醒。

`schema_cmd` 管的是另一件事：**生成器的手工输入槽是这套东西唯一会腐烂的面，也最容易是唯一没人检查的面。** 实测（`FB-20260803-002`）：某项目的渲染器写 `Array.isArray(progress.awaiting_user) ? progress.awaiting_user : []`，而输入里那个字段实际是一个 944 字符的字符串 ⇒ 取空数组 ⇒ 渲染出的「等用户拍板」变成「(无)」，而里面躺着 11–12 条真实待拍板事项，其中一条自标「上线前必办」。三道检查全绿：渲染成功、新鲜度通过、发布前置门只看新鲜度不看内容。于是那份被规定为「任何会话动手前必须先读」的文件，**对每一个接手会话谎报「没有任何事等你拍板」**。

`enforced_by` 管的是第三条：**写下门的名字，是为了让「其实一道都没挂上」这件事无法含混过去。** 实测同一个项目：`staleness_cmd` 确实会红（报清单落后 2 个提交、发布凭据自动作废），但 CI 工作流零命中、无 git hook、仓库自称权威的那份合并协议 11 道门里零命中——**失败是可得的，不是被强制的**。

**诚实边界**：以上是**计划义务 + 评审抽查**。插件在业务仓库里没有常驻脚本，**没有任何 hook 会检查这份清单是否存在、`enforced_by` 里写的门是否真的存在、或它是否真的会跑那两条命令**。这与 `references/STATE_MODEL.md` 里台账那条边界同一性质，照实写在这里，免得读者以为有机器兜底。

## 清单

| ID | 阶段 | 一句话判据（做完了长什么样） | 可执行检查命令 | 判档 | 状态 | 证据 |
|---|---|---|---|---|---|---|
| P-01 | 阶段 0 | | `<command>` | machine / human / hybrid | TODO / DOING / DONE / BLOCKED | |

填写要求：

- **一句话判据**：用「做完之后世界上有什么不一样」来写，不写「实现 X 模块」。
  - ✗「重构订单服务」
  - ✓「订单列表页在 3000 条数据下首屏 2 秒内出结果，且导出的 CSV 行数与列表总数一致」
- **可执行检查命令**：一条能跑的命令，退出码即结论。**写不出命令的条目要标 `human` 判档并写明由谁、看什么来判**——允许存在，但不许假装它是机器可判的。
- **判档**：`machine`（命令说了算）/ `human`（人看了算）/ `hybrid`（命令给证据、人下结论）。**统计完成度时三类分开算**，不许把 `human` 条目混进「已自动验证」的数字里。
- **状态**：只有四种。「大致做完」「主要路径完成」一律记 `DOING`。
- **证据**：命令输出摘要、日志路径或活路径证据出处；`DONE` 而证据栏为空的行不算完成。

## 使用规则（这几条是它存在的理由）

1. **冲突时以本表为准。** 对话里的局部清单、计划散文、看板、交接单与本表冲突时，本表赢——尤其是「用户在会话中随口说的那几项」，那正是已经发生过的覆盖路径。
2. **新会话的唯一入口，而且必须真的排在第 1 位。** 恢复上下文时先读这张表 + 跑一次 `staleness_cmd`，再读计划散文。顺序反了就会被散文里最醒目的那段带偏。**两条可检出的要求**（`FB-20260803-003`）：①这张表必须是**已渲染、直接可读**的产物——不能要求读者先敲一条命令才看得到；②仓库里那份「新会话第一读物」的指引（`CLAUDE.md` / `AGENTS.md` / 恢复清单）里，**它必须排在散文型状态文档之前**。实测反例：某项目的 `CLAUDE.md` 指定第一读物是散文型 `STATUS.md`（其「下一步」是 1332 字的嵌套段落），已渲染的可判表排在第二——顺序恰好是反的，而没有任何机制能发现这件事。
3. **报告完成度时报三个数**：本阶段完成 / 全计划完成 / 剩余阶段清单。**只报「你刚才让我做的那几项」是失效模式本身**，不是简洁。
4. **本表不许手工改状态。** 状态由检查命令的输出刷新；`human` 判档的行由人签字并写下签字时的 HEAD。
5. **过期即失败。** `staleness_cmd` 通不过时，任何「已完成」的结论都降级为待重验，不得用于验收或发布。
6. **渲染成功 ≠ 渲染正确**（`FB-20260803-002`）。产物里出现「(无)」「暂无」「N/A」「0 条」这类空态时，**必须能区分「真的没有」和「输入没解析出来」**——分不清就当作后者，按 `schema_cmd` 失败处理。在「唯一真源」的渲染路径上，把不合预期的输入降级成空值/默认值而不报错**是缺陷，不是容错**，以下写法一律禁止：
   - `Array.isArray(x) ? x : []`
   - `x || {}` / `x ?? []`
   - `parseInt(x) || 0`
   - `try { ... } catch { return [] }`

   正确形态是 fail loud：输入不符合约定就让渲染非零退出，并说出是哪个字段、期望什么形状。

参考实现（`leda_erp` 已落地，可照抄结构，也照抄它的缺口）：

- **有的**：`scripts/status/render-status.mjs`（渲染器）+ `scripts/status/check-status-fresh.mjs`（新鲜度）+ `ai-nseos/state/progress.json`（输入槽）+ 根目录 `PROGRESS.md`（已渲染产物，抬头写明「由 `pnpm audit:progress` 生成，请勿手改」、第 5 行记生成时间 + HEAD + 分支、一行一个阶段、显式声明「不可测 ≠ 0%」，38 次提交历史）。另有 7 份阶段验收清单 + 7 个检查脚本 + 变异验证（故意改坏 → 确认转红）——**后两项本模板并未要求，但它们才是把「判据」变成「证据」的那一步**。
- **缺的（照抄时一并补上，否则会造出「只有新鲜度、没有强制力」的半套）**：那些检查一道都没接进强制路径（CI 零命中、无 git hook、自称权威的合并协议零命中）；手工输入槽没有 schema 校验；已渲染的可判表在恢复顺序里排在散文之后。

**本模板只规定必需字段与语义，不规定用什么语言实现渲染器**——业务仓库用自己的技术栈实现即可。判据是那三条（过期能让命令失败、输入非法/被静默降级也能让命令失败、且失败挂在真正会跑的那道门上），不是用了哪个脚本。
